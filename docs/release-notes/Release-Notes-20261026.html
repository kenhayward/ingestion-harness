Watch out for
  • A database migration (202610251200_decomposition_batches) adds conversion batches, their items and a log of actions on delivered documents, and a new job task, decompose. It runs on its own when the API starts.
  • A second migration (202610252220_register_detached_accepted) lets the register of delivered documents record a detached document and an accepted target state. It also runs on its own when the API starts.
  • A third migration (202610261200_decomposition_items_source_key) indexes batch items by source key, so detaching a document stays quick as batches accumulate. It also runs on its own when the API starts.
  • Two more migrations run on their own when the API starts: 202610261330_decomposition_items_link_backfill fills in the link of documents already delivered whose link was missing, and 202610261331_decomposition_items_times records when each document started and finished converting. Documents converted before it show no time. Each item now has startedAt and finishedAt (null until known).
  • An empty heading in a Word file no longer becomes a section titled [], so a document converted again after this change may have fewer sections than before. The text under an empty heading now stays in the section before it, and a heading that sat under an empty one moves up there too: in the target, the next update removes those sections' old topics and makes new ones, instead of updating them in place.
  • New API routes under /api/conversions: the targets that take documents, and batches to create, fill one file at a time, start, discard, list and read, with each item's report. Each item's row also has actions: POST /api/conversions/items/{id}/force (force-load), POST /api/conversions/items/{id}/redeliver (optionally with a replacement file), POST /api/conversions/items/{id}/detach, and GET and POST /api/conversions/items/{id}/accept (accept the target's state: a preview, then a confirmed accept). Each item says whether its document has been detached, its target state accepted, or its refusal superseded by a later run (resolution), and whether its document's versions were never recorded (unversioned). Detach refuses a document that is neither refused as changed in the target nor unversioned (409 not_refused). Operators, designers and administrators may all use them.
  • A new route, POST /api/conversions/items/{id}/reload, loads a document the target no longer has as a new document: it detaches it, if it isn't already, and starts a batch of one that creates it again. It answers 409 not_gone for a document that is neither gone nor detached. Each item has a new field, gone: true when the target refused its update because it no longer has the document. Such an item now reads unresolved, not failed, and detach takes it too. Operators, designers and administrators may use the route.
  • Two more routes: POST /api/conversions/batches/{id}/retry re-runs chosen failed documents of a started batch from their stored files, as one new batch (body {"itemIds": [...], "force": true}, up to 1,000 documents, each once; force left out = as the batch was started; 201 with the new batch; 409 not_finished while an earlier re-run of one of them is unfinished or the batch never started; 422 not_failed for a document that did not fail), and GET /api/conversions/items/{id}/source downloads a document's original Word file. Operators may use both.
  • A document is re-run once: the retry route answers 409 already_rerun, naming the document, for one that was already run again, even when that re-run failed (re-run it from its own batch instead). Each item has two new fields, rerunIn and rerunAt: the batch it was last run again in, and when that batch started (null when it never was). A migration (202610261400_decomposition_items_redeliver_of) indexes items by the item they re-run, so reading them stays quick. It runs on its own when the API starts.

Minor changes

Word documents converted in batches

#329

Word documents can now be converted in batches for a target that takes decomposed documents. A batch is one upload, of a single file, several files or a folder, to one target. Each file goes up on its own, so a large folder never meets the upload limit, and a file that isn't a Word document is refused on its own while the others carry on. Starting the batch queues one job per file, which decomposes the document and delivers it.

Batches start on the new Conversion tab, in the menu for everyone, operators included. Pick a target (only those that take documents are offered), choose files or a folder or drop them on the box, and choose Start. Each file is named by its file name, or by its path in a folder, and the same name run again later updates the same document. Hidden files and Word's lock files are skipped. A bar shows the files going up, a refused file says why on its row, and Cancel throws the unfinished batch away.

Only Word documents (.docx) are taken for now. The same file name or folder path can't be added to a batch twice.

Once started, the batch opens in its own view, which can be reopened later, or after a reload, from its address. It has one row per document, with the outcome: Created, Updated, Already loaded, Duplicate, Changed in target, Read-back mismatch, Unresolved, In flight or Failed, and Queued, Decomposing or Delivering while it runs. Beside the outcome is a line saying more, such as why a file failed. A document in the target has a link to it there. Every row has a Report, showing what converting the file noticed for someone to check, such as an empty heading or a table with no caption. While any document is still under way the rows refresh every few seconds, and the refreshing stops once every document has settled. Needs attention narrows the rows to the documents someone should look at, and Done to the ones that went through or have been resolved. A screen reader hears how many documents are done each time another settles. A document In flight is being delivered by another batch, and its outcome shows there. Under a new batch, Earlier batches lists the batches started before, newest first, each with its documents counted by outcome.

Each document's row offers the actions that apply to it, each run on that one document:

  • Force-load delivers the stored file again as an explicit update. A document that was already loaded is updated, and a duplicate is created as a second document of its own.
  • Redeliver updates the document, optionally from a replacement file. The replacement keeps the original's name in the batch, so a renamed or moved file updates the right document.
  • Detach makes CT Studio forget the document. It stays in the target untouched, and the next run of the same file creates a new document, even when the file hasn't changed.
  • Accept the target's state, for a document someone changed in the target, first shows each changed part with its version before and now. Once confirmed, the next run of that file updates the document, even when the file hasn't changed, overwriting those changes. If it changes again in the meantime, that run is refused again. If the document changed again while the confirmation was open, the confirmation is refused, and the changes must be looked at again. The confirmation needs a tick in I understand the edits in the target will be overwritten. When too many parts changed to list them all, it can't be accepted, and detach is offered instead.

Force-load is offered on a document already loaded and on a duplicate, redeliver on one delivered or refused, and detach and accept on one changed in the target. Once a document has been detached or its target state accepted, its row says so and offers neither again, in every batch that delivered it. A row whose refusal a later run has moved on from says Superseded by a later run, counts as done, and offers neither: only a document refused as changed in the target can be detached, or one the target holds whose versions were never recorded. That one reads Unresolved and offers detach only.

Force-load and redeliver each start a new batch of one, and only one while it runs, however often the action is chosen. The target's version check always applies, so nothing changed in the target is overwritten without being accepted first. Detaching and accepting are recorded with who did it and when.

A single file and then a folder have been taken through every step to a stand-in for a target: created, already loaded, updated, changed in the target, accepted and detached. The next step is converting a sample report through the tab to the first real target.

Conversion: times, links and empty headings

#331

Four things found converting a large report through the Conversion tab:

  • Each row now says how long its document took to convert, such as took 1 min 12 s, and running for 40 s while it is still going.
  • Open in the target now shows for a target that calls its documents maps, including for documents already delivered. It always opens the document itself, never one of its topics or images.
  • An empty heading, which Word shows as nothing, no longer makes an empty section titled []. It is left out, what follows it stays where it was, and the report notes that an empty heading was left out.
  • A file sent again after an earlier attempt that may have reached the target now says why that is safe: it was sent again with the same key as the earlier attempt, so the target can't create it twice.

Load a deleted document again

#332

When someone deletes a delivered document in the target, running its file again could only try to update the document that was gone, and was refused every time. There was no way to load it again.

Now its row reads Unresolved, saying the target no longer has the document (it may have been deleted), and running the file again or force-loading it no longer tries the update. The row offers Load as a new document, and Detach. Load as a new document asks first: it creates a new document in the target from the stored file, because the old one no longer exists there. Once confirmed, it starts a new batch of one, which the row links to, and the document is created again with a new identity in the target. Choosing it twice makes one batch.

Conversion redesigned, and failed documents re-run

#333

The Conversion tab is easier to read, and a batch's failed documents can now be run again.

  • A new batch is one card in three numbered steps: the target, the Word files and the options. The button says what it does, such as Convert 6 documents, and Force-load is a switch. The list of files counts what is ready, skipped and left out, and Clear all empties it.
  • Earlier batches is a table, ten a page: an icon for how each stands, when it started, its target, how many documents, a chip for each outcome, and who started it.
  • A batch opens with its totals and a bar of its outcomes. Each document is one line, as many as fit the window, with pages to step through, a Failed filter and Find a document. Clicking a line shows the document beside the list: why it failed, when it started and finished, its report, its link in the target and the actions that apply. Each line also has a ⋯ menu.
  • Re-run N failed runs the batch's failed documents again from the files uploaded with it, as a new batch, with Force-load kept or not. Re-run this document does it for one. A document is re-run once from a batch: its line then links to the batch it was re-run in.
  • Download original saves a document's Word file as it was uploaded.
  • Load as a new document, for a document deleted in the target, is on the panel and in the line's ⋯ menu, and asks first from either. A deleted document needs attention, and is not among the failed documents to re-run.

A cell merged down a table shows its text once

#334

Some tools that write Word files repeat a merged cell's text in each row it covers. Word hides the repeats and shows the text once, but the converted document showed it once per row that repeated it: seven times in a report's table whose first cell ran down nine rows. The converted document now shows only what Word shows.

Headings leave their numbers and bold to the target

PR to follow

The target numbers headings itself, so a number typed at the start of a heading, such as 2.1 Experiment Name, showed twice once published: 2.1 2.1 Experiment Name. A converted heading now leaves out a typed number like that. Only a number with as many parts as the heading's level counts, so 2.1 on a second-level heading is left out, while 2023 Results or 1.5mg Dose stay as they are.

A converted heading also no longer keeps bold, italic or underline, which Word adds to its headings: the target's publishing theme sets how headings look. Superscript and subscript stay, since they belong to the characters, as in H2O.

A document delivered before is updated in place the next time it runs: its sections keep their ids.

The checks skip local worktrees

#330

For people working on CT Studio itself: the lint and format checks no longer scan other branches' working copies kept inside a checkout, or local analysis output, so they pass when run from the main checkout.
