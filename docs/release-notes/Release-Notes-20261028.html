CT Studio release notes

Wednesday 28 October 2026: PDFs with printed line numbers read in full, their numbers left out everywhere, ruled tables the layout analysis took for pictures read as tables, PDF layout analysis on the GPU, and scanned pages no longer failing OCR at random. PRs #351, #352, #353 and #354.

Contents

Minor changes

  • PDFs with printed line numbers — read in full, and their numbers left out beside tables and figures too
  • Ruled tables taken for pictures — read from their ruling lines, not delivered as images
  • Bullets taken for pictures — given back to their list items, not delivered as images
  • PDF layout analysis on the GPU — optional, about 7 times faster, with the CPU behind it
  • OCR failing with "Data format error" — scanned pages are rendered one at a time

Other updates

  • The PDF reader is version 7, so a PDF's decomposer version is now 1007 (it was 1005 earlier today): a PDF run again is an ordinary update.

Minor changes

PDFs with printed line numbers

#351

On a guideline that numbers every line in its left margin, the layout analysis took most pages for a table of contents: a column of numbers beside lines of text looks like one. The PDF reader drops a table of contents, so most of such a document's text never reached the target, with only a line in the report ("contents and lists on pages …") to show it. On the ICH Q1 draft guideline, 89 of 108 pages were dropped this way, about three quarters of its text. The layout analysis is now given those pages without their margin of line numbers, so it mostly sees ordinary pages of headings and paragraphs. Where it still takes a page for contents, the reader checks that the region reads as contents, with titles and page numbers, before dropping it; one that doesn't is kept as paragraphs, and its pages are listed in the report's first line. On the ICH draft, all but the three real contents pages are now delivered. On those 26 pages headings come out as plain paragraphs: the PDF has no bookmarks to find them by.

Line numbers were also left in on pages that a table or a figure fills, where too few lines are numbered for the page to show it alone. Once a document has shown that it numbers its lines, those pages lose the numbers that stand in the same column and carry on the count from the pages around them. A figure no longer shows the numbers beside it either: it is cropped from where the text starts.

Ruled tables taken for pictures

#352

The layout analysis sometimes takes a table drawn with ruling lines for a picture. It was delivered as an image, with its cells' text after it as loose paragraphs. Such a picture is now read from its ruling lines: its rows and columns are where the rules are, and cells no rule parts are one cell, so a "50 mg" heading over three columns spans them. The table is delivered with its caption, and flagged as read from its ruling lines so a reviewer can check it. A picture that only repeats a table the layout analysis did read, or holds such a table beside the one it missed, is dropped. A picture with anything other than tables in it stays a picture.

On the ICH Q1 draft guideline, matrixing tables A1-4 and A1-5 are now tables, and no longer images.

Bullets taken for pictures

#355

The layout analysis sometimes takes a list item's bullet for a picture of its own. The bullet was delivered as a small image of a dot, flagged as a rendered drawing, and its item as a plain paragraph. Such a picture, small, over no image and holding only a bullet, now joins the text that starts beside it on the same line, which is delivered as a list item with the bullet dropped, as any other. A small picture with no text beside it stays a picture.

On the ICH Q1 draft guideline, the bullet before line 1714 on page 66 is now a list item, and no longer an image.

PDF layout analysis on the GPU

#353

Reading a PDF's layout is most of the time a PDF takes to decompose: about 5 minutes for a 100-page report with 70 tables. On a host with an NVIDIA GPU, CT Studio can now run it there: that report takes 43 seconds on an RTX 5090, and its output is the same as on the CPU. It is off unless turned on, with three lines in the deployment's settings (the layout service's README has them).

The CPU layout service keeps running behind it. If the GPU service is down, runs out of GPU memory (other programs, such as a local model server, share the GPU) or fails, the document is read again on the CPU from its first page, so it is never part read on one and part on the other.

OCR failing with "Data format error"

#354

A document with scanned pages could fail with "PdfiumError: Failed to load document (PDFium: Data format error)", though the PDF was sound. OCR reads several pages at once, and each was rendered to an image at the same moment; the PDF library that renders them cannot do two at once, and failed one of them at random. Pages are now rendered one at a time and still sent to the OCR model together, so OCR takes no longer. A job that failed this way succeeds when it is run again.
