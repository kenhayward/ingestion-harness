Major changes

Other updates

Watch out for
  • A recipe's delivery.publishTo can now be a list of target ids as well as one id. API clients and YAML or GitHub tooling that read it as a string need updating. A recipe with a single target is still stored as a string.
  • Asking for a revision without open feedback now answers add feedback or run the dev samples before asking for a revision (it was add feedback before asking for a revision), and only when the dev runs flagged nothing either. API clients that match the message need updating. The revise preview (GET …/stages/revise/preview) has a new diagnostics field.
  • Every job's segmented event may carry missedKeys and missedKeysTotal. They are information only: no job is sent to review because of them.
  • One new migration runs with the deploy: 202610211000_several_targets. The bridge contract package is now at 0.2.0.

Major changes

Missed headings

#284

A repeating section starts a new block at every match of its anchor, for example one block per Table N of a stability report or one per batch. When the anchor is too strict, some headings start no block: their text is added to the block before them, and every step reading the section then sees two or more tables mixed together. This is easy to miss. In one 102-page report, an anchor that expected the whole table title on one line matched only 30 of the 60 titles, because most titles wrap onto a second line. The recipe made 1,800 model calls per document, three quarters of the rows it extracted came from the wrong table, and the run took four and a half hours. With the anchors fixed, the same kind of document needed one call per table and ran in about 13 minutes.

CT Studio now spots this for you. For each repeating section with a Key, it looks for every heading the key pattern finds in the text (every Table 7:, say) and reports the ones where no block starts. Sections that share one key pattern are judged together, so a recipe with one repeating section per kind of table only reports headings that none of them caught.

Where you see it

  • Workbench > Sections tab: under a sample in the anchor grid, a Missed headings note lists the keys (for example Missed headings: 1, 2, 3, 9 (+26)), the sections they belong to, and the first missed heading's line as it appears in the text.
  • Drafting: the Sections stage now tells the model about missed headings in its anchor round, so a drafted anchor that misses wrapped titles is corrected before it reaches you.
  • Every job: the headings a job's anchors missed are recorded with the job and feed the run diagnostics below.

How to fix a missed heading

  • If the missed headings are the kind of block this section reads, widen the anchor. Titles often wrap over two or three lines, so rather than asking for the whole title on one line, match the start of the title and look ahead across the next lines for the words that identify it. For example, ^\s*Table\s+\d+:(?=(?:(?!Parameter)[\s\S]){0,400}?Dissolution\b[^\f]{0,120}?Results[ \t]*$) starts a block at every Table N: whose title, within its first lines and before the table's Parameter header row, mentions Dissolution and ends in Results. Requiring Results at the end of a line keeps the table of contents out, because its entries end in dot leaders and a page number.
  • If they are a kind of block the recipe does not read, narrow the section's key so it only matches this kind's headings. They then stop counting as missed.
  • A heading that only the table of contents lists, with no body in the document, is also reported: the note cannot tell it from a heading the anchor missed.

Tip: when a document repeats tables of the same shape (one per study, batch or item), use one repeating section per kind of table and one output table per kind, with columns that tell the blocks apart (study, batch, table number). Each step then reads exactly the blocks it fills. The Sections tab help (? beside Anchors) explains both fixes.

Run diagnostics for the revise stage

#287

The Workbench Revise stage used to answer only your feedback and the failures of the latest dev evaluation. It now also gets run diagnostics: what your latest dev test runs of the draft showed, worked out without a model. The model proposes changes for them as for anything else, and you accept or reject them on the usual cards.

What is reported

  • Steps whose calls mostly came back empty. A step reading a repeating section calls the model once per block. When at least 4 calls were made and half or more returned no rows, the step is reported, for example extract_table_8 on report.docx: 29 of 30 calls returned no rows (02:49). This usually means the step only wants some of the blocks: give each kind of block its own repeating section, or narrow the anchor.
  • Columns whose values did not fit. Values that could not be read as the column's type, or broke its limits, are reported with an example, for example assay_purity_results.impurity_1_pct: 3 values did not fit (e.g. <0.05). The model is asked to fix the column's description or limits first, and to make a column text only when its values really are not numbers or dates.
  • Headings no anchor matched, from the missed headings check, for example report.docx: headings 1, 2, 3 (+27) matched no anchor.

How to use it

  1. Save your draft on the Recipe tab.
  2. On the Test runs tab, choose Run on n dev samples and let the runs finish. Runs awaiting review count, and so do runs you approved or whose steps you re-ran.
  3. Open the Revise tab. The What the model will see card now has a Run diagnostics section listing exactly what will be sent. Without finished runs of the current draft it says Run the dev samples to add what they show.
  4. Choose Ask the model for a revision. You no longer need to write feedback first: diagnostics alone are enough. Each proposed change says which diagnostic it answers.
  5. Accept the changes you want, then run the dev samples again to check they helped. The diagnostics refresh from the new runs.

Good to know

  • Only the newest finished run of each dev sample counts, and only runs made after the draft was last saved, so diagnostics always describe the recipe you are editing. A retried run counts only its latest attempt.
  • Holdout samples are never read, as for everything else revise sends.
  • Each list is capped at 20 rows, worst first. For a project allowed to use an external model, every sample the diagnostics mention is listed in the job's external model call event, like the samples whose text is sent.
  • A step served from the Workbench step cache made no calls in that run, so it is not reported. A problem in a step you haven't changed since an earlier run can therefore drop off the list until that step changes.
  • If a run's files can't be read, that run is left out of the diagnostics. Revise still works with your feedback.

Several targets per recipe

#283

The Publish to setting on a recipe's General tab is now a list: tick every target its published outputs should go to. One approval delivers the same publication to each of them, and the job shows how each delivery went. A job is published once every target has it; if one needs attention, the job goes back to review, and approving again delivers to every target once more.

The first ticked target with the Files layout is the Primary one: Results, downloads and data-lake keys read from it. Use the arrows to change the order. A recipe that keeps a single target is stored exactly as before.

Archive targets

#283

A publishing target now has a Layout. Files writes each output at its own key, as before. Archive (whole package) keeps each publication whole, in a folder of its own: every file, the fields and tables as data.json, the graph as graph.ttl, and package.json describing them. Publishing the same file under the same recipe version again replaces it, and deleting the job removes it. The layout is locked while anything uses the target, like its bucket and prefix. A recipe can't publish to archive targets only: it needs at least one Files target to be its primary.

Minor changes

Approving again after a delivery needed attention

#283

When one target's delivery needed attention and the job was approved again, the old problem could send the job straight back to review, and the job page listed a target twice. Each target now counts only its latest delivery.

Reference run progress

#277, #279

The Workbench References tab used to say only Running while reference runs took minutes. Each sample's row now says where its run is (OCR page 3 of 7, Found the sections, Step 2 of 3 · chunk 1 of 2), and a queued run reads Waiting for a worker. While runs are going, a Reference runs strip counts them, and the tab's header names the document being run, for example Running document 2 of 5 · Step 2 of 6.

Other updates

The delivery bridge's contract is now published as a package (@kenhayward/bridge-contract, GitHub Packages), so an external sink can depend on it and run its conformance suite instead of copying the contract. Each tagged release publishes the package's version; this release adds the archive layout and moves it to 0.2.0. The bridge's README explains how a sink installs and pins it.
