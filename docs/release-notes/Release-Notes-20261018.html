CT Studio release notes

Changes since Friday 5pm: PRs #190 to #247, merged between Friday 16 October 2026, 17:20 and Sunday 18 October 2026.

Contents

Major changes

  • Ontology mapping and value nodes — map values to nodes of a class, a new Mapping tab and better automatic matching
  • Workbench drafting — models call tools, a model log, cancel a run, clearer waiting and failures
  • Backup and restore — encrypted whole-stack backups, restored as this deployment or as a copy
  • Publishing targets — S3 destinations managed in the app, chosen per recipe
  • GitHub recipe sync — push, pull and import recipe versions through GitHub
  • User classes and maintenance mode — Administrators, Designers and Operators; take CT Studio down with a message

Minor changes

  • In-app help — a ? on every page and tab, and one Help dialog in the account menu
  • Workbench and recipe editor refinements — Steps renamed Pipeline, publish from Document types, a clearer Sections table

Other updates

Watch out for
  • The user role is now designer. API clients that send or read role: "user" need updating.
  • New migrations are named YYYYMMDDHHMM_description.sql, not numbered.
  • Zod 4's default error wording has changed.

Major changes

Ontology mapping and value nodes

#237, #238, #239, #241, #242, #243, #244, #245, #247

Recipes can now map a field or column to a value node: a node of a chosen class that holds the value and its unit. Class-centric ontologies such as AFO and OBI describe data this way, and the earlier mapping forms couldn't express it. The new form is in both the TypeScript and Python recipe formats, rendering, SHACL and validation, and the mapping stage proposes it.

The recipe Mapping tab is now an outline beside a single-item editor and shows terms by their readable names. The Workbench Mapping stage reviews proposals in that same outline, with NEW/CHANGED/REMOVED tags and confidence for each change.

A research write-up and an evaluation harness come with it, including a per-output matcher and a covalidation gold file. On the local 27B model, value-as accuracy went from 0/35 to 33/35 over these PRs, and class accuracy from 0/35 to 24/35. The mapping stage also no longer fails when the model uses local terms it hasn't declared.

Workbench drafting

#231, #233, #234

Drafting models can now call tools while they work (ADR 0016):

  • Sections tests its anchors on the dev samples.
  • Revise can read more pages of a sample.
  • Mapping can search the pinned ontologies beyond its shortlist.

The progress line shows which tool is running. Every run now writes a model log of prompts, replies and tool calls, opened with a Model log button. Admins can turn tool calls off per endpoint.

A run can be cancelled, and a queued run now says why it is waiting (queue paused, or a retry). A model the server doesn't have now goes to review at once instead of being retried. Pipeline proposals put their steps in order instead of failing, and a retry replaces the previous reply instead of adding to it.

Backup and restore

#225, #227

Administration > Backup makes one encrypted .ctbak file. It holds the Postgres dump, the bucket objects and the triple store.

A restore uploads the file in resumable parts and checks all of it before changing anything. It then restores into a side database under forced maintenance, and swaps that database in only at the end. There are two modes: as this deployment (everything comes back) and as a copy, for refreshing staging from production, which keeps the target server's own models, publishing targets and settings.

Data-lake key secrets are not included; the restore report lists the consumers whose keys need re-issuing.

Publishing targets

#203, #214

Admins now manage S3 destinations for published outputs under Administration > Published outputs; they are no longer set in .env. A target is either internal (a SeaweedFS bucket) or an external S3 bucket, and each recipe picks one with Publish to. The existing .env target is seeded once as default.

Every delivery records which target it went to, so results, downloads, withdrawals and RDF rebuilds use the right bucket. A target that is in use cannot be removed.

GitHub recipe sync

#196, #228, #229

Recipe versions can be pushed to a GitHub repository, pulled back and imported, so recipes can move between deployments. Each file is a ct-recipe YAML under <root>/<instance>/<type>/v<N>.yaml, and each deployment writes only to its own folder.

Everyone pushes with their own linked GitHub account. When a branch is protected, the push falls back to a pull request. Publishing can push automatically and is never blocked by GitHub. Pulls and imports always create a draft. covalidation v4 was the first recipe pushed this way.

User classes and maintenance mode

#193, #194

There are now three kinds of user:

  • Administrators: everything.
  • Designers: everything except Administration (the old user role).
  • Operators: Home, Jobs (with review) and Results only.

The server enforces operator access with an allow-list, so new routes are closed to operators until they are added to it.

Admins can also switch on maintenance mode with a message. Non-admins then see a banner on the sign-in page and a maintenance page in the app, while queued jobs keep running.

Minor changes

In-app help

#190, #191, #198, #199, #200, #201, #217

Every page, recipe tab, Workbench tab and Administration tab now has a green ? that opens a help topic in a standard wide dialog. All topics are also collected in a Help dialog in the account menu, with an Introduction and a menu of main topics that expands to their parts. Any ? dialog can open its topic there.

A new topic isn't finished until it is listed in the Help menu, and a test enforces this.

Workbench and recipe editor refinements

#190, #230, #232

The Workbench Steps stage is now called Pipeline in the UI, matching the recipe editor; ids and routes are unchanged. A Workbench document type can now be published from the Document types page. The RDF box can be ticked before a mapping exists, although publishing still needs one. In the Sections table, Repeats, Key and Key from now sit on a labelled second line.

Administration layout

#195, #214

The Maintenance form and the Users row buttons were fixed. The Add publishing target dialog is now two columns and fits on one screen, and the browser no longer autofills its Id field with a saved email.

Other updates

Versioning, CI and migrations

#202, #204

Every merge to main is tagged with a calendar version YYYY.MM.DD.N (ADR 0014). The version appears at the bottom of the nav, linking to its tag, and at GET /api/version.

A push to main now only tags the build, which saves about 9 minutes per merge. The compose smoke test is a required check. New migrations use UTC timestamps in their names; 0001–0049 keep their numbers.

Dependencies

#197, #205, #213, #215, #219, #220, #226

Ten Dependabot bumps were tested together, including Vite 8 and Anthropic 1.13. Later bumps covered openai, boto3, @types/node and @vitejs/plugin-react 6.

Zod moved to version 4, and OpenAPI generation now uses Zod's own z.toJSONSchema. Dependabot keeps @types/node on Node 24 and now updates vitest and eslint as groups. Postgres 18, Temurin 24 and Node 26 were deliberately not taken.

Deployment and operations

#222, #224, #227

There is a new guide to continuous deployment on Windows hosts (Docker Desktop and WSL2). The post-deploy smoke test now reads the env file the way compose does (CRLF line endings, S3 port, framing headers). An nginx redirect that broke backup uploads was fixed.

Research and docs

#192, #237, #242

An OCR engine benchmark found that olmOCR's slowness and failures came from how LM Studio had loaded it. Loaded fully on the GPU with a 32k context, it reads a page in 4–6 s. The report recommends no CPU OCR engine. There are also new design docs for mapping automation and value nodes.

Test fixes

#211

A sign-in lockout test that failed between 23:45 and midnight now pins the clock.
