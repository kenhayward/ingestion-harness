Watch out for
  • A database migration (202610251200_decomposition_batches) adds conversion batches, their items and a log of actions on delivered documents, and a new job task, decompose. It runs on its own when the API starts.
  • A second migration (202610252220_register_detached_accepted) lets the register of delivered documents record a detached document and an accepted target state. It also runs on its own when the API starts.
  • New API routes under /api/conversions: the targets that take documents, and batches to create, fill one file at a time, start, discard, list and read, with each item's report. Each item's row also has actions: POST /api/conversions/items/{id}/force (force-load), POST /api/conversions/items/{id}/redeliver (optionally with a replacement file), POST /api/conversions/items/{id}/detach, and GET and POST /api/conversions/items/{id}/accept (accept the target's state: a preview, then a confirmed accept). Each item says whether its document has been detached, its target state accepted, or its refusal superseded by a later run (resolution). Detach refuses a document that is not refused as changed in the target (409 not_refused). Operators, designers and administrators may all use them.

Minor changes

Word documents converted in batches

PR #TBD

Word documents can now be converted in batches for a target that takes decomposed documents. A batch is one upload, of a single file, several files or a folder, to one target. Each file goes up on its own, so a large folder never meets the upload limit, and a file that isn't a Word document is refused on its own while the others carry on. Starting the batch queues one job per file, which decomposes the document and delivers it.

Batches start on the new Conversion tab, in the menu for everyone, operators included. Pick a target (only those that take documents are offered), choose files or a folder or drop them on the box, and choose Start. Each file is named by its file name, or by its path in a folder, and the same name run again later updates the same document. Hidden files and Word's lock files are skipped. A bar shows the files going up, a refused file says why on its row, and Cancel throws the unfinished batch away.

Only Word documents (.docx) are taken for now. The same file name or folder path can't be added to a batch twice.

Once started, the batch opens in its own view, which can be reopened later, or after a reload, from its address. It has one row per document, with the outcome: Created, Updated, Already loaded, Duplicate, Changed in target, Read-back mismatch, Unresolved, In flight or Failed, and Queued, Decomposing or Delivering while it runs. Beside the outcome is a line saying more, such as why a file failed. A document in the target has a link to it there. Every row has a Report, showing what converting the file noticed for someone to check, such as an empty heading or a table with no caption. While any document is still under way the rows refresh every few seconds, and the refreshing stops once every document has settled. Needs attention narrows the rows to the documents someone should look at, and Done to the ones that went through or have been resolved. A screen reader hears how many documents are done each time another settles. A document In flight is being delivered by another batch, and its outcome shows there. Under a new batch, Earlier batches lists the batches started before, newest first, each with its documents counted by outcome.

Each document's row offers the actions that apply to it, each run on that one document:

  • Force-load delivers the stored file again as an explicit update. A document that was already loaded is updated, and a duplicate is created as a second document of its own.
  • Redeliver updates the document, optionally from a replacement file. The replacement keeps the original's name in the batch, so a renamed or moved file updates the right document.
  • Detach makes CT Studio forget the document. It stays in the target untouched, and the next run of the same file creates a new document, even when the file hasn't changed.
  • Accept the target's state, for a document someone changed in the target, first shows each changed part with its version before and now. Once confirmed, the next run of that file updates the document, even when the file hasn't changed, overwriting those changes. If it changes again in the meantime, that run is refused again. If the document changed again while the confirmation was open, the confirmation is refused, and the changes must be looked at again. The confirmation needs a tick in I understand the edits in the target will be overwritten. When too many parts changed to list them all, it can't be accepted, and detach is offered instead.

Force-load is offered on a document already loaded and on a duplicate, redeliver on one delivered or refused, and detach and accept on one changed in the target. Once a document has been detached or its target state accepted, its row says so and offers neither again, in every batch that delivered it. A row whose refusal a later run has moved on from says Superseded by a later run, counts as done, and offers neither: only a document refused as changed in the target can be detached.

Force-load and redeliver each start a new batch of one, and only one while it runs, however often the action is chosen. The target's version check always applies, so nothing changed in the target is overwritten without being accepted first. Detaching and accepting are recorded with who did it and when.
