CT Studio release notes

Tuesday 20 October 2026: publishing through the delivery bridge, recipe plugins and model logs. PRs #248 to #275, merged between Sunday 18 October 2026, 15:27 and Tuesday 20 October 2026, 15:56 (UTC).

Contents

Major changes

  • Publishing through the delivery bridge — a new service delivers every publication and keeps target credentials
  • Connections — external S3 credentials move to the bridge's connections page
  • The triple store through the bridge — graphs are delivered by the bridge, to a Triple store target
  • Recipe plugins — steps that run code instead of a model call
  • Output limits and check plugins — flag values outside a range or pattern, and check them against a list
  • Model logs — see what the model was sent and what it answered, attempt by attempt
  • Mapping memory — mappings designers accepted are reused by later mappings

Minor changes

  • The Delivering status — jobs wait for their deliveries, and show each target's outcome
  • Graph views — cards and a diagram wherever a document's graph is shown
  • Results — a grouped list with a preview, and a result as an outline
  • About and release notes — the build's version and these notes, from the account menu
  • Symbol characters in Word documents — degree signs and other symbols are read as what they show

Other updates

Watch out for
  • Two new settings are required: BRIDGE_CLIENT_KEY and BRIDGE_SECRETS_KEY. Keep BRIDGE_SECRETS_KEY with LLM_SECRETS_KEY: a restore needs both.
  • The publishing-targets API no longer accepts credentials. A request with accessKeyId or secretAccessKey gets a 400; name a connection with connectionId instead.
  • Jobs have a new status, delivering. API clients that list statuses need updating.
  • Re-running an unknown step now answers no extract or plugin step "…" (it was no extract step "…"). API clients that match the message need updating. Rows of GET /api/plugins now carry kind.

Major changes

Publishing through the delivery bridge

#253, #256, #260, #265

A new service, the delivery bridge, now does all publishing. The worker still renders the outputs, then hands the bridge one package per document. The bridge writes the files to the recipe's publishing target, retries what can be retried, and reports each delivery back to CT Studio. Objects land at the same keys as before, so data lakes reading the publish bucket see no change.

Results, downloads, withdraw on delete, republish and RDF rebuilds also go through the bridge, including for outputs published before this release. See ADR 0017 and the deploy guide's Delivery bridge section.

Connections

#260

Credentials for external publishing targets now live on the bridge, not in CT Studio. On Administration > Published outputs, Manage connections opens the bridge's connections page, where admins add, test and rotate S3 credentials. An external target picks one of these connections; internal targets use the deployment's own storage.

On upgrade, each external target's keys move to a connection named after the target, and CT Studio's copy is cleared. Nothing to re-enter: test the target after upgrading to confirm.

The triple store through the bridge

#264, #269

Graphs now reach the triple store through the delivery bridge too. When the deployment has one (RDF_ENDPOINT), it appears under Administration > Published outputs as Triple store, and its connection under Manage connections. A recipe that delivers RDF sends one package: its outputs and its graph's versioned copy go to its own target, and its graph to the triple store. Graph names, copy keys and the loaded Turtle are unchanged, and an older version never replaces a newer one when retries arrive out of order.

The worker no longer connects to Fuseki: the bridge holds the writer's password (RDF_WRITER_PASSWORD). Ontology loads, rebuilds and re-mints go through the bridge as well; a rebuild job now waits in Delivering until its graphs are loaded.

Recipe plugins

#262, #266, #267, #268, #270

A recipe step can now run a plugin instead of asking a model. A plugin is code installed with CT Studio. The first one, text.pattern@1, fills fields or a table by matching patterns in the step's sections: fast and free for values the document always labels the same way. Add one with Add plugin step on the Pipeline tab. Its settings form is laid out from what the plugin asks for, and the Workbench can preview it on the dev samples before any test run.

Publishing checks that the deployment's workers have each plugin and that its settings fit, so a recipe never fails at run time for a missing plugin. Administrators can add plugins as Python packages, installed in the worker image with the WORKER_PLUGINS build argument. The plugin author's guide explains how to write one.

Plugin steps can also:

  • ask the step's model, under the project's data policy, when the plugin needs one;
  • read a repeating section, once per occurrence, as an extract step does;
  • be re-run from the Review page, with guidance for the plugin;
  • enrich an earlier table: fill only some columns of the rows another step found, for example a batch's expiry date printed elsewhere in the document. Extract steps can do this too. Each column is still filled by exactly one step, and re-running the step that finds the rows re-runs the steps that enrich them.

Output limits and check plugins

#271, #272

On the Outputs tab, the Allowed values column sets limits for each field or column: a minimum and maximum for numbers, and a pattern and maximum length for text. A value outside its limits is kept exactly as the document has it and flagged for review, from a step's answer and from a reviewer's correction alike. The model is never told the limits, so it reports what the document says.

A check step can now name a check plugin instead of comparing two outputs. The built-in list.lookup@1 checks values against a list kept in the step, such as approved product names, with the same near-match rules as today's checks. Values it can't match send the job for review, and a plugin's notes show on the Review and Results pages.

Model logs

#273, #275

You can now see what the model was asked and what it answered wherever a model runs. Every model log opens in the same two-panel view: the attempts on the left, marked accepted or sent back, and the attempt you pick on the right. It shows the errors that sent the answer back first, then the prompt, any tool calls and the reply.

  • Pipeline steps: a step that "Needs a retry on many runs" now has See the model log, listing the recent runs that needed a retry.
  • Review page: the Steps tab has a Model log for each step that called a model in that job.
  • Workbench drafting: the existing Model log of Survey, Outputs, Sections, Pipeline, Mapping and Revise proposals uses the same view, for accepted, rejected and failed runs.

Mapping memory

#248, #250, #251

CT Studio now remembers the ontology mappings designers accept, from saves, accepted proposals and publishing. The mapping stage uses that memory before it asks the model. Mappings confirmed across recipes are proposed straight away, and answers designers refused are no longer offered. Mappings are never learned from sample data, and wording from a local-only project never reaches an external model.

The Ontologies page has a Remembered mappings tab to confirm, edit or reject what was learned. Mapped terms now show what they mean wherever they appear: their other names, their definition and a link to the term in the Ontologies page.

Minor changes

The Delivering status

#260

Once the bridge accepts a job's package, the job shows Delivering until every delivery finishes. It then succeeds, fails, or goes back to review with the target and the reason (for example, rejected credentials). The job panel lists each target's delivery. A delivering job can't be cancelled.

Graph views

#254, #255

A document's graph no longer shows only as Turtle. The Review page's Graph tab, the Mapping preview and a published result offer Cards (one card per entity, with each value's evidence and any shape problems on the row they are about), a Diagram, and Turtle.

Results

#252

The Results list groups results by publish day beside a preview panel. A new Show filter picks reviewed, auto-approved or with-issues results. A result opens as an outline (fields, each table, checks, issues and files) beside the item you pick.

About and release notes

#249

About in the account menu, or the version at the bottom of the nav, shows this build's version, a link to it on GitHub, and these release notes by date.

Symbol characters in Word documents

#274

Word documents store characters from the Symbol and Wingdings fonts, such as the degree sign in 25 °C, in a way that read as nothing in the text the model received. The model wrote 25 C. They are now read as the characters they show.

Other updates

Backups include the bridge's connections, still encrypted, and a restore re-registers the publishing targets with the bridge. The post-deploy smoke test now publishes a job through the bridge, reads it back and withdraws it.

The worker was reorganised into self-contained steps with one gate for model calls and the data policy (#257, #258, #259), with no change in behaviour. A trial of running a recipe's steps with LangGraph is included but off by default (#261).
