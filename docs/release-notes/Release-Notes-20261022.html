CT Studio release notes

Thursday 22 October 2026: one registry of publishing targets.

Contents

Major changes

  • One registry of publishing targets — the delivery bridge holds every target; CT Studio shows what it holds

Minor changes

  • A worker that starts first waits — no job is delivered to a target CT Studio hasn't synced yet, and none waits more than 30 minutes
  • Restores and targets — a restore puts back the targets the bridge lacks
  • Other systems to deliver to — the delivery bridge delivers to registered external sinks too
  • Your own connections — everyone can keep their own logins on the connections page

One registry of publishing targets

Publishing targets now live in one place: the delivery bridge. Administration > Published outputs lists the bridge's targets, and every save goes to the bridge first, so nothing is stored when the bridge refuses a change or can't be reached. A target the bridge no longer has is tagged Not on the bridge and can't be edited. Upgrading moves nothing: every target keeps its bucket, prefix, layout and connection, and every published output stays where it is.

The triple store's endpoint is now read from its bridge connection, whose summary shows only the fields that are not secret. The bridge refuses a destination setting its sink doesn't know. For integrators: the bridge contract package is now 0.3.0 (connection summaries carry fields).

A target of another kind of sink is listed, read-only, but recipes can't deliver to it yet: a recipe naming one can't be published (<id> is a <sink> target: recipes can't deliver to it yet), and a copy restore treats production's like its external targets.

A worker that starts first waits

Only the API creates the default and triple store targets now, on its first start. A worker that starts earlier waits for them, and the job is retried without using up its attempts. It waits before any model call, so waiting never re-runs a paid extraction. A job that has waited 30 minutes fails with publishing target <id> has not synced with the delivery bridge for 30 minutes: check that the bridge is running and read the API's log.

Restores and targets

After a restore, targets CT Studio has but the bridge lacks are put back on the bridge. A copy restore keeps this server's targets, so a change made directly on the bridge and not yet shown in CT Studio is overwritten.

Other systems to deliver to

The delivery bridge can now deliver to other systems besides S3 and the triple store. A deployment registers each one in BRIDGE_SINKS. Administration > Published outputs lists them under Systems. Add target > Other system adds a target of one, with the fields that system asks for. Recipes can deliver to such a target alongside an S3 target, which still serves Results and downloads.

These systems are deliver-only for now. Nothing withdraws from them, and deleting a job says what stays there. While a target is in use, its fixed fields are locked; its name patterns are not. For integrators: the bridge contract package is now 0.5.0. The sink catalog lists each sink's fields, and the conformance suite expects a sink to take files and data.

Your own connections

Profile has a new Connections tab. Some systems CT Studio will deliver to record who delivered each item, so they need a real person's login. You keep those logins on the delivery bridge's connections page: Manage connections opens it in a new tab, for every role. You hold one connection for each instance of a system, and only you can see or change yours. CT Studio never sees what you enter: Profile shows each connection's name, system, instance, status and when it was last used.

When an admin disables a user, that user's connections are deleted, and enabling them again does not bring them back. No built-in system uses personal connections, so until one is added the tab says No system here uses personal connections yet. For integrators: the bridge contract package is now 0.4.0 (connection summaries carry kind, instanceId and lastUsedAt, sinks list their instances).
