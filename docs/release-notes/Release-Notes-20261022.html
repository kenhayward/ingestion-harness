CT Studio release notes

Thursday 22 October 2026: a new Review workspace, occurrence filters and parallel model calls, and one registry of publishing targets. PRs #289 to #301, merged between Wednesday 21 October 2026, 14:06 and Thursday 22 October 2026, 10:17 (UTC). #298, delivery to other systems, is described under Major changes and is not merged yet.

Contents

Major changes

  • A resizable Review workspace — the document and the data side by side, with an outline of fields and tables
  • Occurrence filters — a table step reads only its own kind of block
  • Parallel model calls — a step's calls run at once, up to each model's limit
  • One registry of publishing targets — the delivery bridge holds every target; CT Studio shows what it holds
  • Other systems to deliver to — the delivery bridge delivers to registered external sinks too
  • Names where content is delivered — name patterns per target, and names a reviewer can change
  • Delivered as the right person — the approver, a warning at upload, and receipts on the job

Minor changes

  • A tighter Review page — a one-row header, long values shown whole, and page columns that open their page
  • Cancel test runs — stop a queued or running run, or a whole batch
  • Sections: spaces and repeated keys — a fix for no-break spaces, and a warning for keys caught twice
  • Your own connections — everyone can keep their own logins on the connections page
  • A worker that starts first waits — no job is delivered to a target CT Studio hasn't synced yet, and none waits more than 30 minutes
  • Restores and targets — a restore puts back the targets the bridge lacks

Other updates

Major changes

A resizable Review workspace

#299

The Review page, and the read-only view of a finished job, is now one workspace that fits the window. The document and the extracted data sit side by side. Drag the divider between them, or focus it and use the arrow keys (Home and End jump to the ends), or pick 30 / 70, 40 / 60 or 50 / 50. Either side folds to a narrow rail when you need the room, and Swap sides puts the document on the right. Your arrangement is remembered in this browser.

Page thumbnails run beside the page, with a dot on pages holding a flagged field. The tabs that used to wrap onto several lines for a document with many tables are now an outline: Fields, each table (a trailing reference such as (Table IX) on a second line), Edits, Steps and Graph, each with its number of flagged values. Find a table or field narrows the outline, and Next flagged walks through every flagged value as before.

An open table offers All rows or Flagged only, buttons to the previous and next table, and headings that stay in place as you scroll. When Next flagged lands on a value, or you focus one, a strip under the table says why it was flagged, with Edit value while the job awaits review. Below 1,000 px wide the two sides stack. The Review help has new sections on arranging the page and finding a value.

Occurrence filters

#295

A recipe's table step reading a repeating section used to read every block of it. A stability report with 60 tables of 7 kinds in one repeating section made about 960 model calls per document, most of them returning no rows. A step can now say which blocks it reads: on the Pipeline tab, Occurrences takes a pattern matched against the start of each block (its first 600 characters, ignoring case), and the step reads only the blocks that match. None matching means no call and no rows. A filtered step shows a filtered chip, and the Checks strip warns when steps filling different tables all read every block of one section.

The Workbench Pipeline stage now proposes these filters, and checks its first answer once against the dev samples' blocks: a filter matching nothing, or a kind of heading no filter reads, goes back to the model. It also drops chunkPages on a step whose blocks are short. On the example report that is about 60 calls instead of 960, each on one table.

The extraction prompt now puts the chunk and block lines just before the document text, so a local model server can reuse the rest of the prompt between calls.

Parallel model calls

#296

A step's calls (one per block of a repeating section, or per chunk of pages) read separate text, so they can now run at the same time. Administration > Models has a Parallel calls setting beside Max output for each offered model: how many calls may go to it at once, from 1 to 32. Empty means one at a time, as before. The limit holds across every worker together, and OCR uses the OCR model's setting when it has one.

Results are merged in the same order as a run one call at a time, so the extracted data is the same. Steps themselves still run one after another, because a step can read the ones before it. Some local servers answer slightly differently when they batch requests, so compare a test run before relying on a higher value.

One registry of publishing targets

#293

Publishing targets now live in one place: the delivery bridge. Administration > Published outputs lists the bridge's targets, and every save goes to the bridge first, so nothing is stored when the bridge refuses a change or can't be reached. A target the bridge no longer has is tagged Not on the bridge and can't be edited. Upgrading moves nothing: every target keeps its bucket, prefix, layout and connection, and every published output stays where it is.

The triple store's endpoint is now read from its bridge connection, whose summary shows only the fields that are not secret. The bridge refuses a destination setting its sink doesn't know. For integrators: the bridge contract package is now 0.3.0 (connection summaries carry fields).

A target of another kind of sink is listed, read-only, but recipes can't deliver to it yet: a recipe naming one can't be published (<id> is a <sink> target: recipes can't deliver to it yet), and a copy restore treats production's like its external targets.

Other systems to deliver to

#298

The delivery bridge can now deliver to other systems besides S3 and the triple store. A deployment registers each one in BRIDGE_SINKS. Administration > Published outputs lists them under Systems. Add target > Other system adds a target of one, with the fields that system asks for. Recipes can deliver to such a target alongside an S3 target, which still serves Results and downloads.

These systems are deliver-only for now. Nothing withdraws from them, and deleting a job says what stays there. While a target is in use, its fixed fields are locked; its name patterns are not. For integrators: the bridge contract package is now 0.5.0. The sink catalog lists each sink's fields, and the conformance suite expects a sink to take files and data.

Names where content is delivered

#298

A system that names what it creates, a document name for example, takes a name pattern such as {field:title|source.stem}. A target holds one, and a recipe can set its own for that target under Publish to, with a preview. Admins can Browse… a system's spaces or folders instead of typing them.

On the review screen, Names shows what each such target will call the document. Type another name to use it instead. When the system already holds a different document under that name, the job comes back to review with the name marked, so you can choose another. For integrators: the bridge contract package is now 0.6.0, with name patterns and naming inputs, and recipe patterns sent with each delivery.

Delivered as the right person

#298

A system that records who delivered each item gets the approver, or for a document published without review, the uploader. The approver is now recorded by account, so renaming a user no longer loses it. When the person has no connection to that system, or it is refused, the document comes back to review with Manage connections. It no longer stops in Needs review. Fix the connection and approve again.

Uploading to a type that delivers to such a system warns you first when you have no connection there. The upload still goes ahead. Once delivered, the job shows links to what the system wrote, where it gives them. For integrators: the bridge contract package is now 0.7.0, with POST /v1/deliveries:preflight.

Minor changes

A tighter Review page

#301

The Review page's header is now one row: the back link, the file name (cut short when it is long, with the full name on hover), its status, the recipe, version and model, the queue with Next document, and help. The reasons a document needs review moved from a full-width box into an amber Why review chip beside the status, which opens them in a small panel. It only shows while the document awaits review: a finished job no longer shows the reasons it once had. The document and the data get the height the header gave back.

A long value now wraps in its box, so you can read all of it, and editing a text value opens a box that grows with what it holds (you can also drag it taller): Enter saves and Shift+Enter starts a new line.

When a table has a page column (named Page, Page no., Page number, Source page and the like), its page numbers are links that turn the document to that page. Next flagged turns to a flagged row's page as well, and that page's thumbnail gets a dot.

Cancel test runs

#292

The Workbench Test runs tab can now stop runs. Each queued or running run has Cancel, and a batch with unfinished runs has Cancel batch…, which cancels only those runs and leaves finished ones alone. Both ask first, and a batch lists the files it will cancel. A cancelled run can be retried as before, and cancelling works for retired document types too.

Sections: spaces and repeated keys

#291

An anchor that misses a heading only because the document writes a no-break space (or another Unicode space) where the anchor has a plain one now gets a suggested fix on the Sections tab, which names the character and quotes the line. One click applies it, as for the other suggestions.

A sample now shows Keys caught more than once when one key starts more than one block of a repeating section, usually because the anchor also caught the table of contents. It names the section and where each block starts. The Sections drafting stage gets both hints too.

Your own connections

#297

Profile has a new Connections tab. Some systems CT Studio will deliver to record who delivered each item, so they need a real person's login. You keep those logins on the delivery bridge's connections page: Manage connections opens it in a new tab, for every role. You hold one connection for each instance of a system, and only you can see or change yours. CT Studio never sees what you enter: Profile shows each connection's name, system, instance, status and when it was last used.

When an admin disables a user, that user's connections are deleted, and enabling them again does not bring them back. No built-in system uses personal connections, so until one is added the tab says No system here uses personal connections yet. For integrators: the bridge contract package is now 0.4.0 (connection summaries carry kind, instanceId and lastUsedAt, sinks list their instances).

A worker that starts first waits

#293

Only the API creates the default and triple store targets now, on its first start. A worker that starts earlier waits for them, and the job is retried without using up its attempts. It waits before any model call, so waiting never re-runs a paid extraction. A job that has waited 30 minutes fails with publishing target <id> has not synced with the delivery bridge for 30 minutes: check that the bridge is running and read the API's log.

Restores and targets

#293

After a restore, targets CT Studio has but the bridge lacks are put back on the bridge. A copy restore keeps this server's targets, so a change made directly on the bridge and not yet shown in CT Studio is overwritten.

Other updates

Removing targets, and the deployment's own storage

#290

A publishing target can now be removed once every delivery to it has finished. Its id stays taken, so a new target with the same label gets <id>-2 and never inherits the old one's delivery history. An external connection pointing at this deployment's own storage can no longer write into CT Studio's own buckets or the bridge's staging bucket (bucket <b> is reserved). Moving old target keys to the bridge keeps any connection an admin already chose.

Bridge events

#289

The bridge stops resending an event CT Studio still doesn't know after 24 hours (a job deleted during delivery, for example), and logs a warning. A delivery that has finished stays finished: a late event can no longer move it back.
