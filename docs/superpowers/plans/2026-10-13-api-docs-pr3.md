# API docs PR 3: Configuration routes (Specs, Templates, References & regression)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Document the 18 Configuration routes with full descriptions and response schemas.

**Architecture:** As PRs 1–2: route `schema` blocks (documentation only), the docs sweep and the
response conformance hook. Response types that are interfaces become Zod schemas with `z.infer`
types of the same name, next to where they are defined today.

**Tech Stack:** as PR 1.

**Spec:** [docs/design/api-docs.md](../../design/api-docs.md)

## Global Constraints

- No runtime behaviour change; handlers and error messages untouched.
- Every status code a handler can send is documented with its exact message.
- Types keep their names and shapes; `npm run typecheck` proves every consumer still compiles.
- Each route leaves `UNDOCUMENTED`; `npm run openapi` regenerates `docs/openapi.json`.

## Review Focus

1. Template records hold definitions "as authored": drafts may be invalid, so the record's
   `definition` is documented as an open object, never `TemplateSchema` (a draft-save test sends an
   invalid draft; conformance must accept it).
2. `GET /api/specs/{id}` returns either a legacy spec or a template (`kind` discriminates); both
   appear in the suite.
3. The Workbench refusals on publish and import (`publish {id} from the Workbench (holdout
   gate)`) and the reference pinning 409 are documented with their messages.
4. `GET /api/templates/{id}/references` with and without `version` (two behaviours) are both
   described.
5. Regression with no references (400) and the export's YAML content type are documented.
