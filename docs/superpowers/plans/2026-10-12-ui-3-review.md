# UI redesign PR 3: Review page. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild the Review screen as the handoff draws it:
- a header with the review queue position and **Next document**, plus a "Why this needs review" banner;
- a **Source PDF** pane that jumps to a value's page, next to an **Extracted data** pane with counted tabs and **Next flagged**;
- a fields grid with boxed values that show their flag and edit state;
- a decision bar fixed to the bottom of the screen, with the reject reason entered inline.

**Architecture:**
- **Pure logic:** the queue position, the list of flagged targets and cycling through them are pure functions in `apps/web/src/review/queue.ts`.
- **Components:** `ReviewPage.tsx` is split into `ReviewHeader`, `SourcePane` (the existing `PageViewer`, restyled), `FieldsGrid`, `TableTab`, `EditsTab`, `StepsTab` and `DecisionBar`. `ReviewPage` keeps loading and state.
- **Data:** the review needs the jobs list for the queue. `App.tsx` passes the shell's polled `jobs`, so no new API call is needed.

**Tech Stack:** React 19, Vitest + Testing Library.

**Spec:** `docs/design/ui-redesign/SPEC.md` §2 (Review), `FEATURES_AND_API.md` rows 10–12 and 14. Screenshots: the handoff's `02-review*.png` (scratchpad).

## Global Constraints

- **Header:**
  - a back link "‹ Jobs" above the H1 (the file name);
  - a meta row: "<template name> · v<N>", a `StatusPill`, and the model in mono;
  - on the right, "<k> of <n> awaiting review" and **Next document ›**. Next document goes to the next `awaiting_review` job in `createdAt` order, wrapping around. It is hidden when there's no other one.
- **Banner:** "Why this needs review" with `role="note"`, warn tone, listing `reviewReasons`.
- **Panes:**
  - Source PDF: `section aria-label="Source PDF"`, with Previous/Next page icon buttons, "Page X of N", and the hint "Click a value to find it on the page".
  - Extracted data: `section aria-label="Extracted data"`.
- **Tabs:**
  - `Fields <n>`, one per table `<name> <rows>`, `Edits <n>`, `Steps <n extract steps>`.
  - A tab with flagged content shows its count in amber.
  - `role=tablist` / `tab` / `aria-selected` stay.
- **Next flagged:** `Next flagged (<n>)` cycles through flagged fields and cells, switching tabs as needed and focusing the target. It is hidden when there are none.
- **Fields grid:**
  - **Field:** a button with the name and `id · type`; it selects the field and jumps to its page.
  - **Value:** a boxed value.
    - Flagged: amber border, with the flag text below it.
    - Edited: info border with "Edited by X · was Y".
    - A pencil icon button named `Edit <field name>` opens the existing inline editor.
  - **Evidence:** the quote and a "p. N" button.
- **Decision bar** (sticky to the bottom):
  - Reviewer (remembered in `ih.reviewer`), "Note (optional)", **Reject…** and **Approve and publish**.
  - Reject… swaps the note for "Rejection reason (required — rejecting is final)" with a danger border, plus **Keep reviewing** and **Reject document** (danger fill). Reject document is disabled until a reason is entered.
  - Succeeded jobs get the "Save as reference" bar (unchanged); other statuses get a read-only line (unchanged).
- **Unchanged behaviour:**
  - a legacy-spec job shows the `NOT_A_TEMPLATE` note;
  - re-run form fields and semantics;
  - edits reload the review;
  - the list editor uses comma-separated values;
  - read-only outside `awaiting_review`.
- **Layout:** the panes wrap below about 1000 px, and there's no horizontal page scroll at 390 px.

## Review Focus

1. **Next flagged when nothing is flagged, or after the last flag is fixed by an edit.** The button hides, or the count updates; it never points at a stale target. Test in Task 3.
2. **Next document while the current job isn't in the queue** (a succeeded job viewed read-only). It shows "<n> awaiting review", without a position, and goes to the oldest one. Test in Task 1.
3. **Reject… then Keep reviewing.** The reason clears, the note field returns, and nothing is sent. Test in Task 4.
4. **A field with no page.** Selecting it doesn't change the page or fail. Test in Task 3.
5. **The queue updates while reviewing** (the poll removes the current job after a decision elsewhere). The header recomputes without crashing. Test in Task 1.

### Task 1: Queue and flagged-target logic

**Files:**
- Create: `apps/web/src/review/queue.ts`
- Test: `apps/web/test/review-queue.test.ts`

**Interfaces:**
- Produces:
  - `reviewQueue(jobs: readonly JobSummary[], currentId: string): { position: number | null; total: number; next: string | null }`;
  - `type FlagTarget = { tab: 'fields'; field: string } | { tab: string; row: number; column: string }`;
  - `flaggedTargets(view: EffectiveView, template: ReviewData['template']): FlagTarget[]`, in display order (fields first, then tables in template order, rows ascending, columns in order);
  - `targetKey(t: FlagTarget): string`, which builds `field:<id>` or `<table>:<row>:<column>`.

- [ ] **Step 1: Write the failing tests**

```ts
import { describe, expect, it } from 'vitest';
import { effectiveView } from '../src/review/effective.js';
import { flaggedTargets, reviewQueue, targetKey } from '../src/review/queue.js';
import { job } from './fake-api.js';
import { reviewData } from './review-fixture.js';

describe('reviewQueue', () => {
  const at = (id: string, minute: number, status = 'awaiting_review' as const) =>
    job({ id, status, createdAt: `2026-10-12T10:${String(minute).padStart(2, '0')}:00Z` });
  const jobs = [at('c', 30), at('a', 10), job({ id: 'x', status: 'succeeded' }), at('b', 20)];

  it.each([
    ['a', { position: 1, total: 3, next: 'b' }],
    ['b', { position: 2, total: 3, next: 'c' }],
    ['c', { position: 3, total: 3, next: 'a' }], // wraps
    ['x', { position: null, total: 3, next: 'a' }], // not in the queue: oldest first
    ['gone', { position: null, total: 3, next: 'a' }], // polled away
  ])('%s', (id, expected) => expect(reviewQueue(jobs, id)).toEqual(expected));

  it('has no next when the current job is the only one', () => {
    expect(reviewQueue([at('a', 10)], 'a')).toEqual({ position: 1, total: 1, next: null });
    expect(reviewQueue([], 'a')).toEqual({ position: null, total: 0, next: null });
  });
});

describe('flaggedTargets', () => {
  it('lists flagged fields, then flagged cells in order', () => {
    const data = reviewData();
    data.document.issues.push({ step: 'head', target: 'kind', row: null, column: null, raw: 'x', message: 'not an option' });
    const targets = flaggedTargets(effectiveView(data), data.template);
    expect(targets.map(targetKey)).toEqual(['field:kind', 'results:2:batch', 'results:2:value']);
  });

  it('drops a target once it is edited', () => {
    const data = reviewData({
      edits: [{ id: 1, at: '', field: null, table: 'results', row: 2, column: 'value', oldValue: 'Complies', newValue: '98', editor: null, reason: null }],
    });
    expect(flaggedTargets(effectiveView(data), data.template).map(targetKey)).toEqual(['results:2:batch']);
  });
});
```

  Check `ReviewEdit`'s exact fields in `packages/shared` before running, and match them in the fixture.

- [ ] **Step 3: Implement `queue.ts`.**
