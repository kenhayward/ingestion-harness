# UI redesign PR 4: Results page. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild the Results list as the handoff draws it:
- document-type chips and a file name filter, done server-side;
- download links on each row;
- a preview panel with the fields and the first table rows, plus links to the full result and the source PDF.

**Architecture:**
- **API addition A3:** `ResultSummary.outputs` lists each row's published files, so a row can link its downloads without a call per row.
- **API addition A4:** `GET /api/results` takes `q`, a case-insensitive file name substring.
- **Contract:** both are TS-only (`packages/shared` Zod, `IngestionRepo.listPublished` in `MemoryRepo` and `PgRepo`).
- **Web:** `ResultsPage` gets chips, a debounced filter, a list and a `ResultPreview` panel. The existing `ResultDetailView` (#/results/:id) is unchanged.

**Tech Stack:** Fastify + Zod, Postgres, React 19, Vitest.

**Spec:** `docs/design/ui-redesign/SPEC.md` §3 (Results), `FEATURES_AND_API.md` A3, A4 and rows 15–17. Screenshot: the handoff's `03-results.png`.

## Global Constraints

- **`outputs`:** `ResultSummary.outputs: { outputId: string; format: 'csv' | 'json'; name: string; rowCount: number | null }[]`.
  - It covers published outputs only, ordered by `outputId`.
  - `name` is the object key's base name.
  - `outputCount` stays.
- **`q`:** trimmed, 1 to 100 characters after trimming (blank means absent), validated by Zod.
  - It's a case-insensitive substring match on the file name.
  - `%`, `_` and `\` are matched literally (escaped, `ESCAPE '\'`).
  - Paging cursors work with `q`.
- **Header:** "Results" + "Published outputs in the target store. Test runs and rejected documents never appear here."
- **Toolbar:**
  - document-type chips: All types, then one per type, sorted by title;
  - a file name field with `aria-label="Filter by file name"`, debounced 250 ms into `q`.
  - The top-bar search on this page fills the same field (a single server-side filter).
- **List:** Document (a button that selects the row into the preview) · Document type · Published · Reviewed by · Issues · Download.
  - Issues shows "—" for 0 or unknown, and amber 600 otherwise.
  - Download has one link per output, via `api.outputUrl(jobId, outputId, { stage: 'published' })`.
  - "Load more" keeps the cursor paging.
- **Preview:** `aside aria-label="Result preview"`, containing:
  - the file name;
  - "<type> v<N> · published <when> · reviewed by X" (or "auto-approved");
  - the fields as a key/value list;
  - the first 3 rows of the first table;
  - **Open full result** (`#/results/<id>`) and **View source PDF** (`api.documentUrl(id)`).
  - Legacy spec results say "No preview for this document type."
- **Selection:** the first row by default; the selection falls back like Jobs. The detail page (`ResultDetail`) is untouched.

## Review Focus

1. **A file name containing `%` or `_`.** The filter matches it literally, not as a wildcard. Test in Task 1 (both repos).
2. **Typing quickly in the filter.** Only the last value is requested after 250 ms, and an older response can't overwrite a newer one. Test in Task 3.
3. **The preview fails to load** (the target store is down, or the document is invalid). An inline note appears, and the list keeps working. Test in Task 4.
4. **A result with no published document JSON** (legacy spec, or only CSVs). The preview says so and still offers the links. Test in Task 4.
5. **Load more with a filter active.** The cursor and `q` are both sent, so the next page keeps the filter. Test in Task 3.
