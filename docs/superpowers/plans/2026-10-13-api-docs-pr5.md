# API docs PR 5: the rest of the Workbench, the S3 keys, and no more undocumented routes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Document the last 26 routes (Drafting stages & proposals; Evaluation, iterations &
comparisons; Feedback & revise; Holdout & publish gate; Data-lake S3 keys), then delete the
`UNDOCUMENTED` allow-list so every route must be documented.

**Architecture:** As PRs 1–4. View interfaces in `@ih/shared` and the S3 key types in the API
become Zod schemas with `z.infer` types of the same name. `ProposalViewSchema` moves to
`drafting.ts` (it needs `ChangeBodySchema`; `workbench.ts` only imports types from `drafting.ts`,
so no value cycle).

**Tech Stack:** as PR 1.

**Spec:** [docs/design/api-docs.md](../../design/api-docs.md)

## Global Constraints

- No runtime behaviour change; handlers and error messages untouched.
- Every status code a handler can send is documented with its exact message.
- The S3 key routes are admin-only (`x-admin: true`); their 404 when the publish target is not
  the local SeaweedFS is documented.
- The holdout rule is stated wherever it applies (drafting, feedback, comparison, revise).

## Review Focus

1. `POST …/stages/{stage}` covers every stage including `references` (reference runs) and
   `revise` (needs open feedback), with the stage-order 409.
2. Proposal decisions: partial acceptance, the version and per-change conflict 409s, and that
   accepting a revise proposal resolves its feedback.
3. Publish below the gate: 409 without an override reason (with `gate`), 400 for a short reason,
   409 when the draft changed while publishing.
4. Iteration views are large (scorecard, per-sample comparisons): their schema must accept the
   running and complete states the tests produce.
5. After the allow-list goes, a new route without docs fails `npm test` with its name.
