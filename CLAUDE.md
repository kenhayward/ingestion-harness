# CLAUDE.md

Content Transformation Studio (CT Studio; repo and code name `ingestion-harness`): ingests PDFs whose structure is known in advance, extracts their contents
through an LLM prompt harness, and writes validated CSV/JSON to S3 (SeaweedFS).

## Architecture in one paragraph

`app` (React, served by nginx) → `api` (Fastify, Node 24/TypeScript) stores the uploaded PDF in
the SeaweedFS **inbox** bucket and inserts a `documents` row + `jobs` row in Postgres. The
`worker` (Python 3.14) claims jobs with `SELECT … FOR UPDATE SKIP LOCKED`, extracts page text
(OCR'ing image-only pages with a vision model, default olmOCR 2), segments it into sections using the document **spec**, runs one LLM call per spec extraction
(JSON Schema-constrained, validated, retried with errors fed back), and writes CSV/JSON to the
**outputs** bucket plus a prompt/response audit trail to the **runs** bucket. Full detail:
[docs/architecture.md](docs/architecture.md). Decisions: [docs/adr/](docs/adr/).

## Layout

```
apps/api/            Fastify API          src/app.ts = composition root (buildApp(deps))
apps/web/            React + Vite UI      components take an `Api` port as a prop
packages/shared/     Zod schemas + types shared by api & web (spec format, job DTOs, key helpers)
worker/              Python worker (uv)   src/ingest_worker/{pipeline,extract,segment,outputs,queue,llm/}
specs/<id>/v<N>/     Document specs: spec.yaml + prompts/*.md.j2 (immutable once published)
config/              llm-providers.yaml (providers, discovery, model aliases)
db/migrations/       Forward-only SQL migrations (shared by api and worker)
deploy/              docker compose, Dockerfiles, deploy/dev scripts (.sh + .ps1)
.github/workflows/   CI (GitHub-hosted) + deploy (self-hosted)
```

## Test-driven development — how we work here

1. **Red first.** For every behaviour change, write or extend a failing test, run it, and see
   it fail for the expected reason before touching implementation. Bug fixes start with a test
   that reproduces the bug.
2. **Green minimally**, then refactor with the suite green. Run the narrowest test command while
   iterating, and `npm run check` before declaring work done.
3. **Never weaken a test to make it pass** (deleting assertions, loosening matchers, adding
   skips). If a test is wrong, say why and fix it deliberately.
4. **Ports and adapters keep tests fast and offline.** Unit tests never touch the network,
   Postgres, SeaweedFS, or a real LLM:
   - API: `buildApp({ repo, store, specs, … })` with `MemoryRepo` + `MemoryObjectStore`;
     exercise routes with `app.inject()` (see `apps/api/test/helpers.ts`).
   - Web: components receive an `Api` prop; tests use `fakeApi()` from `apps/web/test/fake-api.ts`
     and Testing Library queries by role/label (not class names).
   - Worker: `PipelineDeps` takes `MemoryObjectStore`, a `TextExtractor` lambda (no real PDFs
     needed), and a `ModelRegistry` of `FakeProvider`s; queue behaviour via `FakeQueue`
     (`worker/tests/fakes.py`). Provider adapters are tested against stub SDK clients
     (`tests/test_providers.py`) that assert the exact request shape.
   - Code needing real infra (PgRepo, PgJobQueue, S3 stores) gets integration tests marked
     `@pytest.mark.integration` (excluded by default) or under `apps/api/test/integration/`.
     `npm run test:integration` runs the API ones (own config). The workbench Pg test skips unless `IH_TEST_DATABASE_URL` is set; point it at a throwaway Postgres
     (they apply `db/migrations` and write rows), e.g. `docker build -f deploy/docker/postgres.Dockerfile -t ih-postgres:pgvector deploy/docker`
     once (Postgres 17 with pgvector, needed from migration 0035), then `docker run --rm -d --name ih-test-pg -e
     POSTGRES_PASSWORD=test -p 55433:5432 ih-postgres:pgvector`, then
     `IH_TEST_DATABASE_URL=postgres://postgres:test@localhost:55433/postgres npx vitest run --config apps/api/vitest.integration.config.ts workbench-pg`.
5. **Contract tests stay green**: both `apps/api/test/spec-registry.test.ts` and
   `worker/tests/test_specs.py` load every spec in `specs/`. A new spec is not done until both pass.
6. New pure logic (segmentation, CSV flattening, retry policy, alias resolution) should be
   table-driven/parametrised tests — cheap to extend when a new document quirk turns up.

## Rules of the road

- **Templates live in the database** (`templates` table, migration 0003; `apps/api/src/templates/`, `apps/web/src/templates/`): drafts editable, published immutable (DB triggers too), YAML import/export, `specs/*/template.yaml` seeded on API start. The worker loads a job's template from the DB first (`pipeline.load_definition`), files second. Draft test runs set `jobs.test` and are never delivered to the target (approving one only finishes review). Every write to a draft records a `template_changes` row for every document type, not only Workbench ones (migration 0029, append-only, `ON DELETE CASCADE` from its version, so `deleteDraft` takes the log; published rows are never written and the 0003 triggers are untouched) in the same statement (a data-modifying CTE in `PgTemplateRepo`): `hand` saves (`PUT …/versions/:version`, also the Sections tab's anchor saves), applied `proposal`s (with `stage`, `proposal_id`; ` (n of m proposed changes)` when partly accepted), `restore`d iterations, the draft's `started` entry (new type v1, next draft "from published vN", Workbench project creation) and `import`s (YAML as a draft, bundles); summaries and diff chips come from `describeDefinitionChange`, and a write that changes nothing (`count` 0, an absent list = `[]`) logs nothing, nor do published creates (seed, published import). A save may carry `baseUpdatedAt` (both editors send it): when the draft was written since, nothing is saved or logged and the answer is a 409 `the draft changed since you opened it; reload it to see the changes` (Pg compares `updated_at` truncated to the millisecond, since it keeps microseconds and the API's ISO strings milliseconds); the editors disable Save while a save is in flight (a double click would otherwise 409 against its own first save) and offer *Reload the draft*. Accepting a proposal and restoring an iteration pass the `updatedAt` of the draft they read as `expectedUpdatedAt`: a write in between (a hand save) is a 409 `the draft changed while applying; try again` with nothing written or logged (a draft that was published meanwhile keeps the `…no longer open` wording). Renaming a document type (`PUT /api/templates/:id/name`, `renameTemplate`; the Document types card's *Rename…*, `RenameDialog`; refused for a retired type) writes the trimmed name (1-200 characters) into the open draft as a `hand` change `Renamed “old” to “new”` (under `expectedUpdatedAt`: a write in between is a 409 `the draft changed while renaming; try again`), starting the next draft from the latest version first when none is open (published versions keep their name), and renames the Workbench project at once (`WorkbenchRepo.renameProject`); the same name changes nothing and starts no draft.
- **Version labels (issue #144, migration 0045):** every recipe version may carry a `label` (1-80 chars) and a `note` (1-2,000) with `label_set_by`/`label_set_at` (`VersionLabelBodySchema`, `PublishLabelSchema`, `VersionLabelSchema`, `versionName` in `packages/shared/src/version-labels.ts`; `TemplateRecord` carries them, `TemplateRepo.setLabel`). Metadata only, never part of the definition: the 0003 trigger guards `definition`/`status` alone, so published versions take labels; setting one leaves `updated_at` alone (the editors' `baseUpdatedAt` still matches) and logs nothing in `template_changes`; the worker never reads it. Routes (`routes/templates.ts`): `PATCH /api/templates/:id/versions/:version` (a field left out is kept, `null` clears; retired types too), `GET /api/templates/:id/versions` (newest first, no definition; `GET /api/templates` `versions[]` carry `label`), `POST /api/templates/:id/versions/:version/restore` `{ from, baseUpdatedAt? }` (writes version `from` into the open draft as a `restore` change ` (from vN · label)`; nothing written when equal; 409 `{id} v{n} is not an open draft` or the stale-draft message). Both publish routes take optional `label`/`note`, set on the draft first. A new draft's `started` entry names its source's label. Web: the recipe editor's *Versions* sub-tab (`VersionsPanel`, both editors; outside the read-only fieldset): label and note per version, *Replace draft vN with vM* (confirm `Dialog`, disabled while edits are unsaved) or *Start vN from vM* when no draft is open; publish keeps the draft's label (no publish dialog).
- **Retired document types (migration 0030):** an admin retires or unretires a type (every version, recipe or legacy spec) with `PUT|DELETE /api/specs/:id/retirement` (admin-only, logged `document type retired`/`unretired`; retiring again keeps the first retirement; unretiring a type that is not retired is a 204; unknown is a 404). The row (`document_type_retirements`: `type_id`, `retired_at`, `retired_by` = the user's name) lives with the type, not a version, so seeding a missing `specs/*/template.yaml` version keeps the type retired, and deleting a never-published Workbench project removes it. Nothing is deleted and everything stays readable, except what the type delivered: retiring withdraws it (ADR 0011 step 7: `IngestionRepo.withdrawType` marks its jobs' published outputs `job_outputs.withdrawn_at` (migration 0037), forgets its current graphs and queues one `withdraw` job, on every PUT, idempotent (it never repeats a failed withdrawal: `withdrawalStatus.failed` counts failed and needs-review ones for the Linked data panel); readers skip withdrawn outputs; the worker's withdrawal spares what was delivered again since, checked under each graph's lock (`GraphRegistry.locked`, `RebuildSource.object_live`)), and unretiring queues a `republish` (`republishType`) that re-delivers them from each job's reviewed document, else its draft, with its own recipe version (nothing if the type was retired again; graph before the record; legacy spec outputs are skipped and stay withdrawn). Hidden: `GET /api/specs` by default (`?retired=include` lists them with `retired`; every row carries `kind`; Jobs, Home and Results ask for them so old jobs keep their names; the upload strip never offers one), the Document types page always (no toggle), the Workbench list by default (`retired=include` for API callers, no toggle in the web; `ids=` still returns them, so pinned and recent cards show them with a *Retired* tag and the project URL opens). `GET /api/templates` and every `ProjectView` carry `retired`; the Workbench list overlays it live (never cached; `LIST_CACHE_VERSION` 4). New work is a 409 `<name> is retired: unretire it to use it again` (`retiredProblem`, the `refuseRetired` preHandler): uploads and Templates test runs, retry/re-process of any of its jobs, regression runs, a new type under a retired legacy id, new drafts, publishing (both routes), YAML import, Workbench project creation, bundle import under that id, sample uploads, dev test runs, every drafting stage, holdout reference runs, re-verify, evaluate and compare. Allowed: reading, edits that queue no job (draft, brief, feedback, proposals, skip/keep, restore, policy, threshold, sample role), deletes, cancel, review of jobs already awaiting review (approve, reject, step re-run), saving a reference, anchor previews and bundle export. Jobs already queued or running finish (the worker is unchanged). Web: admins retire any type, recipe or legacy, from the Document types page (*Retire…* and a confirm `Dialog`, `RetireDialog`); the page lists file-only legacy `spec.yaml` types as read-only cards (`legacyTypes` in `apps/web/src/templates/legacy.ts`: `kind: 'spec'` rows of `GET /api/specs` with no database recipe; tag *Legacy spec (file)*). **Unretiring is API-only**: there is no Unretire button anywhere and no `unretireType` in the client; `RetiredBanner` (project page, standalone recipe editor) and the *Retired* tags say who retired the type, when, and name `DELETE /api/specs/{id}/retirement` (`unretireHint`). A retired type's recipe editor is read-only (like a published version). The web disables each job-creating button with `RETIRED_REASON` (`apps/web/src/ui/retired.ts`); the Jobs page and Runs tab Retry buttons are not pre-disabled (the dialog shows the 409).
- **Document templates (`template.yaml`) are the preferred format** — outputs first (fields + typed tables), steps compile to the engine's `Extraction` (`template.compile_step`), run by `template_pipeline.py`. Legacy `spec.yaml` still runs via `pipeline.py`; both share `prepare_document` (OCR, copies, page markers, sections).
- **Specs are immutable once published.** Change a document type by adding `specs/<id>/v<N+1>/`;
  jobs record the spec id + version they ran with. Prompts are Jinja2 with `StrictUndefined`.
- **Migrations are forward-only**: add `db/migrations/NNNN_description.sql`; never edit an
  applied one.
- **LLM endpoints in the database ([ADR 0010](docs/adr/0010-llm-endpoints-in-the-database.md), phases 1-4):** `llm_endpoints`, `llm_models.curated`, `llm_choices` and `llm_settings` (migrations 0024, 0027; `llm_aliases` of 0024 became choices and settings in 0027) hold the running config. `config/llm-providers.yaml` (its `${VAR}` values: `ANTHROPIC_MODELS`, `OPENAI_MODELS`, `LOCAL_LLM_MODELS`, `DEFAULT_MODEL`, `FAST_MODEL`, …) and `LLM_ENDPOINTS` (`name=baseUrl|m1,m2[|local|external[|kind]]`, `;`-separated; keys in `LLM_ENDPOINT_KEYS=name=key;…`, resolved by `registry.endpoint_key`) are defaults the worker seeds on start (`seed_from_config` -> `PgLlmConfigStore.seed`): a row an admin edited (`edited_at`, `curated_edited_at`) or added (`source = 'ui'`) is never changed, an env row gone from .env is removed, and an unchanged .env moves nothing. The worker builds its registry from the store (`LiveModels`, every stored endpoint optional: no key = skipped) and rebuilds it (`main.refresh_models`, every `CONFIG_CHECK_S`) when `llm_config_state.version` moves (triggers on endpoints, aliases, curation; `NOTIFY ih_llm_config`). The store contract (`tests/test_llm_endpoints.py`) runs on `MemoryLlmConfigStore` and, with `IH_TEST_DATABASE_URL` (a throwaway database: it empties `llm_*`), on Postgres. - **LLM layer** (`worker/src/ingest_worker/llm/`): providers implement the `LLMProvider`
  protocol (`list_models`, `complete_json`). `complete_json(…, on_tokens=)` streams the reply and reports a growing token estimate (`TokenCounter`: text plus thinking or reasoning, about four characters a token); only Workbench drafting passes it, so every other call is made as before. Kinds: `anthropic`, `openai-chat`,
  `openai-responses`; any OpenAI-compatible local server is an `openai-*` provider with
  `baseUrl`. Model refs are `provider/model-id` or an alias from `config/llm-providers.yaml`

  `anthropic/claude-haiku-5-5`). Unresolvable refs raise `ModelResolutionError` and are resolved

  for a local-only project before any call, in extraction, OCR (after `resolve_ocr`; the OCR clone

- **Workbench ([ADR 0007](docs/adr/0007-workbench.md), [design](docs/design/workbench.md)):** one project per document type (`workbench_projects.id` = template id; `apps/api/src/workbench/`, `apps/api/src/routes/workbench.ts`, `apps/web/src/workbench/`). The Workbench page is the paged project list: it asks `listProjectPage` (`GET /api/workbench/projects`) for one page, counts the filter chips from the server's `facets`, debounces the search by 250 ms (a sequence number drops stale responses), shows up to 3 pinned (`/api/workbench/pins`) and recent (`ih.wbRecent` in `localStorage`, written by `ProjectPage`) projects as cards, and keeps the rows per page in `ih.wbPageSize`. Samples are ordinary documents; uploading one queues a `prepare` job (text + OCR only, `worker/src/ingest_worker/workbench.py`) writing `prepared/{sha256}/text.json|triage.json` to the runs bucket. Sample state comes from that job. Workbench jobs (prepare and test runs) have `priority = -10` (production 0). Prepare jobs never appear on the Jobs page and are never bulk-deleted; while a sample prepares, the worker writes `prepare progress` job events (text layer read, then each OCR page) and, on a `DocumentError`, a `prepare failed` event whose `message` is the review reason; `SampleView.prepare` shows the current attempt's progress only (event at or after the job's `updatedAt`) and `SampleView.prepareStatus` (`queued`|`running` while preparing, else null) tells waiting from working; the Samples tab (#142) shows each preparing sample's page count once known (`samplePages`), a bar and percentage (`prepareFraction`: waiting 0, reading 5%, text layer 10%, OCR pages to 100%), and, while anything uploads or prepares, a *Preparing samples* strip (`batchProgress`) with the files still uploading and their byte progress (`uploadSample(…, onProgress)` posts through XMLHttpRequest); the list refreshes after each upload, and `prepareError` trusts a code only while its message equals the job's error (else `other`); pypdf password/read errors in `prepare` go to review instead of being retried; brief history: `GET /api/workbench/projects/:id/briefs` (`briefVersions` in `packages/shared/src/brief.ts`: `changedSections` = `briefDiff` against the previous version, `usedBy` = stages whose newest accepted or partially accepted proposal used that version) and `GET …/briefs/:version`, the Brief tab comparing versions client-side with `briefDiff`; dev test runs are ordinary test jobs: `POST …/test-runs` takes optional `sampleIds` (1-200 unique uuids; ready dev samples only: an unknown id or a holdout sample is a 400, one not prepared a 409, all checked before anything is queued) and stamps every job of the call with one `params.batchId`; `GET …/test-runs` returns `TestRun`s (the job summary plus a running extraction's `progress` from its latest `step progress` event of this attempt) for every project job except `prepare` and except runs of holdout samples (holdout stays sealed there); reference and evaluation runs and runs from before batches have `batchId: null`. `GET /api/queue/summary` (any signed-in user, counts only) gives `ahead` (queued jobs with a document: production, prepare, publish, rerun and earlier Workbench runs; document-less drafting, segment and export jobs are not counted), `running` and a rough `etaSeconds = ceil(ahead × median / max(1, running))` (`queueSummary`, `IngestionRepo.queueStats`; the median is over the 50 newest succeeded or awaiting-review runs that finished in the last 24 h; null without history, 0 for an empty queue). A sample's document is never deleted with a job. Anchor previews are `segment` jobs: project-scoped with no document (`document_id IS NULL`, excluded from every `JobSummary` query by the inner join), `priority = -5`, one per project (a new preview deletes the old; previews for one project serialize via `pg_advisory_xact_lock`). They run `segment.section_spans`, the same code production segmentation uses, in a child process capped at 10 s (`SEGMENT_TIMEOUT_S`); on overrun the child is killed and the job goes to `needs_review` ("…may backtrack catastrophically"), so a runaway anchor regex cannot stall previews or other jobs on the same worker (previews are capped; production segmentation is not, so the Sections tab refuses to save an anchor whose preview timed out). Every grid carries `suggestions` for required sections that miss a segmented sample: `anchor_hints` suggests only for readable anchors (`^Label`, `^(A|B)\b`, optional `(?i)`, leading `\s*`; anything else gets none), tries the anchor's own labels in another case or indented, then `LABEL_VARIANTS` synonyms longest first (never `from`, `bill`, `po`, `terms`, `item`), accepts a synonym only if it looks like a label (colon, end of line or 2+ spaces after, word ends), verifies the rewrite matches the missing sample (`segment_samples` also drops it if it breaks a sample where the section was found), gives one accurate reason per cause (synonym, case, indent), and runs inside the capped child; the Sections tab applies one with a click (unsaved, previewed live). Segment jobs are never retryable or cancellable through the jobs routes: `PgRepo` guards are `document_id IS NOT NULL`, and any query on `jobs` that bypasses `JOB_SELECT` must exclude document-less rows. Idle workers wake on `NOTIFY ih_jobs` (trigger from migration 0009); the poll interval is the fallback (and drives retry backoff). The UI polls a preview every 300 ms with a 30 s deadline. Drafting ([ADR 0007](docs/adr/0007-workbench.md), phase 3a): jobs are document-less `draft` jobs (`priority = -10`, migration 0011). The API sends only ready **dev** samples and `drafting.build_context` refuses anything else; the worker's example template comes from `WORKBENCH_EXAMPLE_TEMPLATE`. Proposals live in `workbench_proposals`, with status derived from the job and the body in `drafting/{project}/{job}.json` (`storage.drafting_key`). Only an admin can allow external models for a project. External drafting calls are logged as `external model call` job events listing the samples whose text was sent (`samples`, max 8, `MAX_CONTEXT_SAMPLES`) and, in `referencedSamples`, every sample name the sent failures and feedback mention. Drafting stages (phase 3b): stages run in order (`STAGE_ORDER`: survey, outputs, sections, steps); a stage counts as complete once it is accepted or skipped, and stale is derived, never stored. A stale outputs, sections or steps stage can be kept without a proposal (migration 0026 `workbench_stage_confirms`): `POST /api/workbench/projects/:id/stages/:stage/confirm` is 201, 400 `stage X cannot be kept` (survey, references and the rest), 404 unknown project, 409 `stage X is not stale`; the row's `up_to` is the newest earlier completion as read for the check, so a later completion makes the stage stale again (`stageStates` is stale only when an earlier stage completed after `max(completedAt, upTo)`). A kept stage keeps its kind and `completedAt` (a kept skip stays skipped; later stages are unaffected), no proposal is created and the draft is untouched; `StaleBanner` `keepLabel` reads Keep these outputs / anchors / steps. A re-run that proposes no changes is accepted with `changes: []` (`ProposalCard`: Accept: no changes needed; the decision body refuses `[]` for a proposal with changes): the draft is untouched and, once the stage is complete, `stageStates` reads that acceptance as a confirmation up to its decision time (via `ProposalLike.acceptedChanges`), not a new completion, so later stages do not go stale; a never-completed stage is completed by it. `StageView.skippedAt` is the newest skip, kept after a later run (the Survey "You skipped this stage" banner, `skip` tone). Survey "In brief" is `candidateInBrief`, computed client-side and never stored. The Survey tab is four tabs, Findings (summary, variants, document anatomy), Questions, Candidates and Ontologies, each panel kept mounted while hidden; `#/workbench/<id>/survey/<view>` opens one (`Route.view`; Brief links to `questions` and `ontologies`, Mapping to `ontologies`), and Accept/Reject stays below the tabs. Ontology pinning lives on the Survey tab (`SurveyOntologies`: the survey's suggestions with Pin and *Use vN*, evidence, *Also matched* rows with what each adds and their own Pin, *Not covered by the suggestions* with the also-matched ontology and term that would cover each (`uncoveredHints`), *Refresh suggestions* when stale, then the picker moved from the Brief (`BriefOntologies` `title="Pinned ontologies"`) whose changes save at once and the mapping guidance with *Save guidance*, kept unsaved in `ih.ontologyGuidance.<project>`; one brief save at a time on the tab: answers, Pin and the picker share a lock, and the suggestions reload when the survey finishes or is decided); the Brief tab shows a summary line with *Change on Survey* and its kept draft never restores ontology picks; the Mapping tab's empty state and the mapping 409 point to Survey. The confirmations join `projectFingerprints`, and `deleteProject`'s children include stage confirmations. The worker drops empty strings/lists from drafted changes before validation, and removes are checked against the draft after earlier changes in the same body. `applyChanges` and `draft_changes.apply_changes` are held in step by the shared fixture, run in TS with `toStrictEqual` (a TS test also parses worker-shaped dumps). References and evaluation (phase 4a): samples are linked to references by PDF sha256. Reference runs are dev test runs with `modelOverride: 'draft'` and `params.forceReview`, so the worker always stops them in `awaiting_review`; the user corrects the values, approves (review finishes, nothing is delivered) and then uses "Save as reference" on the succeeded job. `start('references')` skips samples whose reference run is still queued or running; the references stage is accepted once every ready dev sample is verified and is never stale (`referencesStage` takes no earlier stages: an outputs change outdates the affected references instead), the References tab hides Skip once the stage is accepted or skipped, and `start('references')` before the earlier stages are complete is a 409. `POST /api/workbench/projects/:id/references/:sid/run` (201) re-runs one ready sample, verified or not, for re-verification (dev: `modelOverride: 'draft'`; holdout: the template's own models; `params.forceReview`; 409 while its run is queued or running; not blocked by the stage order); the detail panel's Re-verify… opens it in `ReprocessDialog`. The scorecard is computed from the jobs, and the summary is cached in `scores` once every job has finished; the evaluation routes rethrow store outages instead of caching a score, and a corrupt or missing document gives a null comparison. Restore writes the snapshot into the open draft. `MemoryRepo` owns the monotonic clock shared by the workbench fake. Feedback and revise (phase 4c): feedback lives in `workbench_feedback` (migration 0015) and can only name dev samples; a feedback `sampleId` must be a READY dev sample and an `iterationId` a dev iteration. `revise` is a change stage outside `STAGE_ORDER`, run as a `draft` job started by `POST /projects/:id/stages/revise`, that cannot be skipped (`StagePanel` `canSkip=false` in the Revise tab), and it may run with no prepared dev samples (feedback alone). Its job params add the open `feedback`, dev-only `failures` from the latest complete dev iteration (the template's own runs first; a model-comparison member only when none is complete), `failuresFrom` (that iteration's `templateVersion` and `model`, shown in the `<evaluation_failures>` header), and `feedbackIds` (only the items actually sent). Each `params.feedback` item carries its `id`, and the API trims `failures` with `revisionFailures` (dev files, lowest score first, at most `MAX_CONTEXT_SAMPLES`), the same rule as the worker's `select_failures`, which is then a no-op. `GET /api/workbench/projects/:id/stages/revise/preview` (handoff RV1, `RevisePreview`) returns exactly what the next revision sends (feedback, failures with `failuresTotal` and `failuresFrom`, the drafting model setting, the open draft, the dev sample files sent, the limits) and `notSent` (ready holdout samples, the newest holdout run: its score only). The prompt labels feedback `F1…Fn`; each revise change's `answers` names the labels it answers, and `draft_stages.resolve_answers` stores them as feedback ids (`DraftChange.answers`, unknown labels dropped). Feedback can only name dev samples and dev iterations (RV3: 400 `feedback can only refer to dev samples` / `… dev iterations`; the web add form never sends a `sampleId` or `iterationId`). The worker drops feedback/failures whose sample is not a dev sample filename in params and sends the lowest-scoring failures, capped at `MAX_CONTEXT_SAMPLES`. Accepting a revise proposal, fully or partly, resolves the feedback its applied changes answer (`answeredFeedback`), or all the feedback it was sent when no change names any (proposals from before RV2). Revise skips the anchor round, but a proposal with `putSection`/`setCopies` changes gets one `segment_with_timeout` pass over the dev samples; a timeout sends the job to `needs_review` (no `anchorCheck` is stored). The revise model schema has no union (nullable) types: payload objects and `answers` are always present with empty sentinels (`""`, `[]`, `0`) that are mapped back to absent, to stay within Anthropic's structured-output limit of 16 union-typed parameters; a test over every stage schema guards this. Holdout and publish (phase 5a, migrations 0016 and 0017): holdout reference runs use the template's own models (`modelOverride: null`, no draft model, since drafting never sees holdout) with `params.forceReview`, started by `POST /api/workbench/projects/:id/holdout/reference-runs` (not a stage); they skip samples that already have a reference or an active run, and refuse with 409 `reference runs are already running` when every unverified holdout sample has an active run. `GET /references?set=dev|holdout` lists either set. Evaluate takes `{ set }` (default `dev`); holdout iterations are visible to the user but ignored by revise (its failures are dev-only), and model comparison stays dev-only. `SampleView.holdoutRuns` is the number of holdout iterations that evaluated the sample, read from `workbench_iterations.sample_shas` (migration 0017, the evaluated samples' sha256 recorded at creation, so the count survives deleted jobs; null rows fall back to the jobs' documents). The publish gate is `publishGate` in `packages/shared/src/evaluation.ts`: the newest complete holdout iteration whose version and definition snapshot equal the open draft and that ran the template's own models (`model === null`; override iterations are allowed for exploration but never count) decides. It passes only when it covered every currently ready holdout sample, compared every sample it evaluated (a job that failed, needs review, was cancelled or deleted fails the gate), and its score is at or above `workbench_projects.publish_threshold` (default 0.9, set with `PATCH /api/workbench/projects/:id`, which records who set it and when: `threshold_set_by` from the user's name, `threshold_set_at`, migration 0020, shown under the threshold on the Publish tab). `gateFor` computes those scores from the jobs and caches them per iteration in `workbench_iterations.gate_cache` (migration 0020) under a fingerprint of its jobs (sha256 of each job's `[id, status, updatedAt, referenceId]` in `jobIds` order, a deleted job as `[id, null, null, null]`): a matching fingerprint reuses the cached score, anything else recomputes, and the cache is stored only once no job is queued, running or awaiting review (coverage is always live). Scores compare the raw draft output (never `reviewed-document.json`, so review edits cannot raise a holdout score; dev iterations still use the reviewed document); `GET /api/workbench/projects/:id/publish-gate` shows it. That route returns `PublishGateView` = `GateView` + `hints` (EV1, `gateHints` in `packages/shared/src/evaluation.ts`): the deciding iteration's fields and `table.column`s strictly below the threshold, worst first (`no_step` before `low_accuracy`, then by key), at most `MAX_GATE_HINTS` (5); `no_step` (`stage: 'steps'`) when no extract step of the draft fills the output (a column takes its table's coverage; undefined keys count as unfilled), else `low_accuracy` (`stage: 'revise'`); empty without a deciding iteration. The overview's `gate` stays a plain `GateView` without hints. `gate_cache` also stores `hints` and `hintsThreshold`: with `withHints` (that route only) a row lacking them (rows from before EV1; no migration) or computed at another threshold is a miss, recomputed and stored again. The web uses `PublishGateView` (`Api.getPublishGate`, `useGate`) and `GateView` (overview, `ProjectHeader`). The gate is informational: References and Evaluate are optional stages (`OPTIONAL_STAGES` in `overview.ts`, with Revise; never the next to-do; but a revision applied to the open draft after its newest evaluation, `OverviewInputs.evaluation.revisedSince`, makes the Next action *Evaluate vN on dev*, `LIST_CACHE_VERSION` 5), Publish is `ready` whenever a draft is open, and `POST /api/workbench/projects/:id/publish` publishes any valid draft, recording the gate's iteration and score (null without a holdout run) and never an override (`overrideReason` is still accepted, then ignored; under 10 characters is still a 400). Publications are logged in `workbench_publications` (`GET /api/workbench/projects/:id/publications`), and publications from before the gate became informational keep their override reason. Bundle (phase 6, migration 0019): `export` jobs are document-less, `priority = -10`, one per project (a new export deletes the old export job and its zip, serialized by `pg_advisory_xact_lock(hashtext('export:' || id))`). `bundle.run_export` checks `ExportParams` (`DraftParams` plus `projectName`), refuses holdout samples, verifies each PDF's sha256, builds `context.md` with `drafting.build_context` (the same inputs as the drafting stages: brief, draft, accepted survey, at most `MAX_CONTEXT_SAMPLES` dev samples' text) and writes a deterministic zip to the runs bucket at `exports/{project}/{job}.zip` (`exportKey`/`storage.export_key`); a cancel or delete during the write removes the zip. Layout: `manifest.json` (`BundleManifestSchema`: format `ih-workbench-bundle`, `formatVersion` 1, optional `completedStages`: the `STAGE_ORDER` stages accepted or skipped at export, typed as those four in `ExportParams`; still format version 1, so deployments running code from before `completedStages` refuse these bundles, the strict manifest schema rejecting the unknown key; likewise a `survey.json` whose candidates carry `seenIn` is refused by deployments from before it, strict `SurveyBodySchema`), `README.md`, `context.md`, `brief.json`, `survey.json` (the accepted survey, only when there is one), `template.yaml`, `stages/<id>.md` + `.schema.json`, `samples/<sha256>.pdf`. Routes (`apps/api/src/routes/workbench-bundle.ts`): `POST /api/workbench/projects/:id/export` (202 `ExportView`), `GET .../exports`, `GET .../exports/:jobId/bundle`; exporting or downloading a local-only project needs an admin (403), and the web hides the Download link from non-admins on local projects; a download whose export carried a sample that is no longer a dev sample of the project (removed or made holdout) is a 409 `a sample changed since this export; export again`. `POST /api/workbench/projects/import` (multipart; optional `id`/`name` fields BEFORE the file, blank = manifest's) unzips with streaming fflate under a cap on the bytes actually inflated (`maxUploadBytes * MAX_SAMPLES + 8 MiB`, also the upload limit), checks the entry count and rejects duplicate entry names, validates everything (manifest, `template.yaml` as a mapping, `brief.json`, every PDF: `%PDF`, size, sha256, no duplicates, the id) before writing anything, then creates template draft v1, a `local` project, the brief (none when the manifest's `briefVersion` is null), the dev samples via `addSampleFile` (each queues `prepare`), and the stage rail: `survey.json` (checked with `SurveyBodySchema`, 400 `survey.json: …`) becomes an accepted survey proposal backed by `Repo.createFinishedDraftJob` (a `succeeded` document-less `draft` job no worker claims; model `imported`), then every other completed stage is skipped in `STAGE_ORDER` (a completed survey without `survey.json` is skipped); an existing id is a 409 (`import under another id`); if creating the project fails the v1 draft is deleted, and a failure after the project exists is a 500 `import failed after creating project <id>; delete the project and import again`. Import streams through temporary files (`apps/api/src/workbench/bundle-import.ts`): the upload is saved to a temp dir under the cap, the metadata entries (`manifest.json`, `brief.json`, `template.yaml`, `survey.json`) stay in memory, at most `BUNDLE_TEXT_ALLOWANCE` (8 MiB) in total (400 `bundle is too large` past it, as for an upload over the limit: busboy truncates the stream, so it is a 400, not @fastify/multipart's 413), each sample PDF is inflated to its own temp file and hashed as it is written, other entries are only counted, and the temp dir is always removed. Deleting a project: `DELETE /api/workbench/projects/:id` (204; 404 unknown; 409 `<id> has a published version; published document types keep their project` once any version is published). `WorkbenchRepo.deleteProject` removes in one transaction. It first locks the type's `templates` rows (`FOR UPDATE ORDER BY version`) and returns `published` (409, nothing written) if any is published, then locks the project row: the same order as `publishDraft` (template row, then the project through the publication FK), so the two cannot deadlock (a Pg integration test races them). - **Error routing in the worker:** `DocumentError` (missing sections, page count, schema never
  satisfied, refusal, `PrepareFailed` in prepare only, a request too long for the model's loaded context window:
  `llm.base.ContextExceededError`, raised by the adapters from `is_context_exceeded` (LM Studio, OpenAI, vLLM,
  llama.cpp, Ollama, Anthropic wordings; a streamed one is not retried whole), routed by `ocr_pages` and
  `run_step_extraction` with `context_exceeded_reason` (stage, model ref, what to lower) and by drafting and
  mapping with `drafting.context_reason`) → `needs_review`, not retried. Anything else → `fail()` → re-queued with
  backoff until `max_attempts`, then `failed`.
  `JobCancelled` (operator cancel, ADR 0005) → no status write; worker status writes are guarded
  `AND status='running'` so a cancel always wins. **One job, one worker:** a claim takes a queued
  job with `FOR UPDATE SKIP LOCKED`, and while it runs a thread beats `jobs.heartbeat_at` every
  `HEARTBEAT_S` (60) on its own connection, guarded like a status write (`heartbeat.py`,
  `PgJobHeartbeat`, `beating`; migration 0042, which also makes `jobs_notify_changed` ignore a
  beat). The reaper re-queues a running job only when its heartbeat (else its claim time) is older
  than `STALE_LOCK_S` (900): its worker stopped (a redeploy), whatever its attempts (`run_once`
  warns past the limit), so `WORKER_REPLICAS` > 1 never runs a long job twice. A run whose job was
  taken anyway stops at its next `check_cancelled`, and embedding checks between batches
  (`embed_version(stop=)`); a retried ontology import whose version is already `ready` only
  finishes its embedding (`OntologyStore.ready`), since saving its terms again would cascade-delete
  the embeddings.
- **Word documents ([ADR 0009](docs/adr/0009-word-documents.md), [design](docs/design/word-documents.md)):** a `.docx` source is converted to PDF by the `converter` service (Gotenberg `8.37.0-libreoffice`, compose network `converter` with `internal: true`, only the worker joins it, `CONVERTER_URL`) before the pipeline, which then runs unchanged. `pipeline.load_source` reads the inbox object, judges `.docx` by its content types (`convert.is_docx`; never a file name: LibreOffice turns any bytes into a text PDF; anything else is read as a PDF as before), and caches the PDF at `converted/{sha256}/{fingerprint}.pdf` in the runs bucket (`storage.converted_key`; fingerprint `gotenberg-{version}-c{CONVERT_VERSION}`; an invalid entry is re-converted). A document's identity is the uploaded file: `Source.sha256` (the `.docx`'s hash, = `documents.sha256`) keys prepared text and the OCR cache, never the PDF's hash (LibreOffice embeds a creation date). `ConversionRejected` (a 4xx, a 500 `LibreOffice failed to convert…`, a non-PDF 200) → `needs_review`; `ConverterUnavailable` (transport, timeout, other 5xx) is retried; no converter configured → `needs_review`. Tests use `FakeConverter` (`tests/fakes.py`); `tests/test_convert_integration.py` (marked `integration`) needs `CONVERTER_URL` (dev-infra publishes the converter on `localhost:3010`). Uploads (`POST /api/documents`, Workbench samples, bundle import) go through `checkSource` (`apps/api/src/uploads.ts`): a PDF, or a `.docx` (not `.docm`/`.dotx`/other OOXML; 415 `file is not a PDF or Word document (.docx)`) without tracked changes (`<w:ins|del|moveFrom|moveTo` in the body, headers, footers, footnotes or endnotes: 422), inflating only those parts under a 64 MiB cap. The inbox key's extension records the kind (`inboxKey(…, ext)`), and `JobSummary`/`ResultSummary.contentType` derive from it (`sourceContentType`; no column, since document rows copied for test, reference and regression runs share the key); `GET /api/jobs/:id/document` serves a `.docx` as an attachment. Bundles carry samples as uploaded (`samples/<sha256>.docx` for Word), and import checks each like an upload and against its extension. The CI smoke test uploads `deploy/scripts/fixtures/smoke.docx` as a Workbench sample and waits for it to be prepared (2 pages; no model call). The upload strip also takes dropped folders (`readDrop` in `apps/web/src/jobs/folder-drop.ts`: entries taken during the drop event, subfolders walked, only `isSourceFile` files listed in path order, hidden files/folders and `~$` Office lock files left out; a drop without a folder is handled synchronously as before) and shows one line per folder (`folderNote`: `Name: n files to process · k other files left out`). The web's upload inputs take `SOURCE_ACCEPT` and filter with `isSourceFile` (`apps/web/src/documents.ts`; by type or `.pdf`/`.docx` name, since browsers often send no type for `.docx`), and a Word job or result offers "Download original (.docx)" (`isWordDocument(contentType)`) instead of "Open PDF".
- **The step cache is workbench-only:** production, regression and re-run jobs never read or write it (`template_pipeline.workbench_step_cache` returns `None` for them).
- **Never call real LLM APIs from tests or CI.** No API keys in the repo; secrets live in
  `deploy/.env` locally (git-ignored) and `/etc/ingestion-harness/<env>.env` on deploy hosts.
- TypeScript: ESM with `.js` import suffixes, Zod at every boundary (env, request bodies,
  specs), no `any` without a comment. Python: `mypy --strict`, ruff, dataclasses/Pydantic,
  `from __future__ import annotations`.
- Keep `apps/api` free of LLM logic and `worker` free of HTTP-serving logic.

## CI/CD

Public repo (Apache-2.0). **CI runs on GitHub-hosted runners**; only deploys use self-hosted
runners on the deploy hosts. Never target a self-hosted runner from a `pull_request` workflow
(see [docs/runners.md](docs/runners.md)). `main` is protected: PRs only, CI must be green.
`ci.yml`: node + worker jobs, then images build + compose smoke test. `deploy.yml`: main →
staging after green CI (once repo variable `AUTO_DEPLOY_STAGING=true`); manual dispatch for production / rollbacks (`no_build` + older ref).

sides · docs/ADR updated if architecture changed · no secrets committed.
