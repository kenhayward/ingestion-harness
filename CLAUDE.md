# CLAUDE.md

Content Transformation Studio (CT Studio; repo and code name `ingestion-harness`): ingests PDFs whose structure is known in advance, extracts their contents
through an LLM prompt harness, and writes validated CSV/JSON to S3 (SeaweedFS).

## Architecture in one paragraph

`app` (React, served by nginx) → `api` (Fastify, Node 24/TypeScript) stores the uploaded PDF in
the SeaweedFS **inbox** bucket and inserts a `documents` row + `jobs` row in Postgres. The
`worker` (Python 3.13) claims jobs with `SELECT … FOR UPDATE SKIP LOCKED`, extracts page text
(OCR'ing image-only pages with a vision model, default olmOCR 2), segments it into sections using the document **spec**, runs one LLM call per spec extraction
(JSON Schema-constrained, validated, retried with errors fed back), and writes CSV/JSON to the
**outputs** bucket plus a prompt/response audit trail to the **runs** bucket. Full detail:
[docs/architecture.md](docs/architecture.md). Decisions: [docs/adr/](docs/adr/).

## Layout

```
apps/api/            Fastify API          src/app.ts = composition root (buildApp(deps))
apps/web/            React + Vite UI      components take an `Api` port as a prop
packages/shared/     Zod schemas + types shared by api & web (spec format, job DTOs, key helpers)
worker/              Python worker (uv)   src/ingest_worker/{pipeline,extract,segment,outputs,queue,llm/}
specs/<id>/v<N>/     Document specs: spec.yaml + prompts/*.md.j2 (immutable once published)
config/              llm-providers.yaml (providers, discovery, model aliases)
db/migrations/       Forward-only SQL migrations (shared by api and worker)
deploy/              docker compose, Dockerfiles, deploy/dev scripts (.sh + .ps1)
.github/workflows/   CI (GitHub-hosted) + deploy (self-hosted)
```

## Test-driven development — how we work here

1. **Red first.** For every behaviour change, write or extend a failing test, run it, and see
   it fail for the expected reason before touching implementation. Bug fixes start with a test
   that reproduces the bug.
2. **Green minimally**, then refactor with the suite green. Run the narrowest test command while
   iterating, and `npm run check` before declaring work done.
3. **Never weaken a test to make it pass** (deleting assertions, loosening matchers, adding
   skips). If a test is wrong, say why and fix it deliberately.
4. **Ports and adapters keep tests fast and offline.** Unit tests never touch the network,
   Postgres, SeaweedFS, or a real LLM:
   - API: `buildApp({ repo, store, specs, … })` with `MemoryRepo` + `MemoryObjectStore`;
     exercise routes with `app.inject()` (see `apps/api/test/helpers.ts`).
   - Web: components receive an `Api` prop; tests use `fakeApi()` from `apps/web/test/fake-api.ts`
     and Testing Library queries by role/label (not class names).
   - Worker: `PipelineDeps` takes `MemoryObjectStore`, a `TextExtractor` lambda (no real PDFs
     needed), and a `ModelRegistry` of `FakeProvider`s; queue behaviour via `FakeQueue`
     (`worker/tests/fakes.py`). Provider adapters are tested against stub SDK clients
     (`tests/test_providers.py`) that assert the exact request shape.
   - Code needing real infra (PgRepo, PgJobQueue, S3 stores) gets integration tests marked
     `@pytest.mark.integration` (excluded by default) or under `apps/api/test/integration/`.
     `npm run test:integration` runs the API ones (own config). The workbench Pg test skips unless `IH_TEST_DATABASE_URL` is set; point it at a throwaway Postgres
     (they apply `db/migrations` and write rows), e.g. `docker run --rm -d --name ih-test-pg -e
     POSTGRES_PASSWORD=test -p 55433:5432 postgres:17-alpine`, then
     `IH_TEST_DATABASE_URL=postgres://postgres:test@localhost:55433/postgres npx vitest run --config apps/api/vitest.integration.config.ts workbench-pg`.
5. **Contract tests stay green**: both `apps/api/test/spec-registry.test.ts` and
   `worker/tests/test_specs.py` load every spec in `specs/`. A new spec is not done until both pass.
6. New pure logic (segmentation, CSV flattening, retry policy, alias resolution) should be
   table-driven/parametrised tests — cheap to extend when a new document quirk turns up.

## Rules of the road

- **Templates live in the database** (`templates` table, migration 0003; `apps/api/src/templates/`, `apps/web/src/templates/`): drafts editable, published immutable (DB triggers too), YAML import/export, `specs/*/template.yaml` seeded on API start. The worker loads a job's template from the DB first (`pipeline.load_definition`), files second. Draft test runs set `jobs.test` and are never delivered to the target (approving one only finishes review).
- **Document templates (`template.yaml`) are the preferred format** — outputs first (fields + typed tables), steps compile to the engine's `Extraction` (`template.compile_step`), run by `template_pipeline.py`. Legacy `spec.yaml` still runs via `pipeline.py`; both share `prepare_document` (OCR, copies, page markers, sections).
- **Specs are immutable once published.** Change a document type by adding `specs/<id>/v<N+1>/`;
  jobs record the spec id + version they ran with. Prompts are Jinja2 with `StrictUndefined`.
- **Migrations are forward-only**: add `db/migrations/NNNN_description.sql`; never edit an
  applied one.
- **LLM endpoints in the database ([ADR 0010](docs/adr/0010-llm-endpoints-in-the-database.md), phases 1-3 and 4a):** `llm_endpoints`, `llm_models.curated` and `llm_aliases` (`default`, `fast`, `draft`, `ocr`; migration 0024) hold the running config. `config/llm-providers.yaml` (its `${VAR}` values: `ANTHROPIC_MODELS`, `OPENAI_MODELS`, `LOCAL_LLM_MODELS`, `DEFAULT_MODEL`, `FAST_MODEL`, …) and `LLM_ENDPOINTS` (`name=baseUrl|m1,m2[|local|external[|kind]]`, `;`-separated; keys in `LLM_ENDPOINT_KEYS=name=key;…`, resolved by `registry.endpoint_key`) are defaults the worker seeds on start (`seed_from_config` -> `PgLlmConfigStore.seed`): a row an admin edited (`edited_at`, `curated_edited_at`) or added (`source = 'ui'`) is never changed, an env row gone from .env is removed, and an unchanged .env moves nothing. The worker builds its registry from the store (`LiveModels`, every stored endpoint optional: no key = skipped) and rebuilds it (`main.refresh_models`, every `CONFIG_CHECK_S`) when `llm_config_state.version` moves (triggers on endpoints, aliases, curation; `NOTIFY ih_llm_config`). The store contract (`tests/test_llm_endpoints.py`) runs on `MemoryLlmConfigStore` and, with `IH_TEST_DATABASE_URL` (a throwaway database: it empties `llm_*`), on Postgres. The pickers offer only curated, enabled models: `ModelInfo.curated` is `llm_models.curated` on an endpoint that exists and is enabled (`PgRepo.listModels` joins `llm_endpoints`), `isOffered` (`packages/shared/src/models.ts`) is what `GET /api/models` lists and what upload and retry overrides must be (400 `unknown or disabled model …` otherwise), and `?all=true` adds disabled models and uncurated discoveries (suggestions). Admin API (phase 3a, `routes/llm.ts`, admin-only, tag Models): `GET/POST /api/llm/endpoints`, `PATCH|DELETE /api/llm/endpoints/:name`, `PUT /api/llm/endpoints/:name/models` (exactly these are curated; new ids are added; withdrawn ones stay as suggestions) over `LlmConfigRepo` (`apps/api/src/llm/repo.ts`, `MemoryLlmConfigRepo`/`PgLlmConfigRepo`; schemas and `resolveAlias` in `packages/shared/src/llm.ts`). Every write is an admin's: `edited_at`/`updated_by` (or `curated_edited_at`), so .env no longer changes it; disabling an endpoint, withdrawing a model or deleting an endpoint an alias resolves to is a 409 `alias {name} uses {ref}: point it elsewhere first`; only `source = 'ui'` endpoints are deleted (an env one is a 409 `… comes from .env: disable it instead`, it would be re-seeded). Keys entered there are AES-256-GCM under `LLM_SECRETS_KEY` (`_PREVIOUS` decrypts during a rotation), stored as `v1:base64(nonce‖ciphertext‖tag)` in `llm_endpoints.api_key_enc` (migration 0025): the API encrypts (`apps/api/src/llm/secrets.ts`, 409 `LLM_SECRETS_KEY is not set: the API cannot store keys` without it) and never returns one (`keySet`), the worker decrypts (`llm/secrets.py`, `cryptography`), a stored key wins over `api_key_env`, and one that cannot be decrypted skips the endpoint (never another key); the fixture `packages/shared/test/fixtures/llm-secret.json` holds both sides in step. Models page (phase 3b, `apps/web/src/models/ModelsPage.tsx`, `#/models`, admins only): an admin's name chip at the top right is a menu (`AccountMenu` in `shell/AppShell.tsx`: Models, Access, Sign out; Escape returns focus to the name; users keep the plain chip with Sign out), and Models is also in the Admin nav. One card per endpoint: kind, where its settings came from (From .env / Edited by / Added here by), Disable/Enable, base URL (inline edit), Location (`Segmented` local/external), key (Set key / Remove key; a stored key shows as `Key stored (encrypted)`, else `Key from .env (VAR)`), and Models offered (checkboxes; discovered ones are tagged suggested; Add a model id; Save models sends the sorted set); Remove endpoint (after a confirm) only for endpoints added here; a refusal shows in the card's alert. Add endpoint is a `Dialog` (name, kind, base URL, location, comma-separated models, optional key). Only offered models run (phase 4a): the worker's registry built from the store (`registry_from_seed` -> `build_registry(offered_only=True)`) resolves a ref, after its aliases and for OCR too, only when the model is in its endpoint's curated, enabled list (`PgLlmConfigStore.load` reads `curated AND enabled`), else `ModelResolutionError` `model {ref} is not offered on endpoint {name}: add it on the Models page` (needs_review, no call); a registry built from the config file alone is not restricted. The API checks with `modelRefProblem` (`packages/shared/src/llm.ts`, over `runnableModels`: the offered refs and stored aliases): a step re-run's `model` must be offered or an alias resolving to one (400), and `templateIssues` (`apps/api/src/templates/definitions.ts`) adds a `pipeline.N.model` issue for an extract step naming a model that is not offered (an alias the database does not define is left to the worker) to the template views and refuses publishing (Templates publish and import, Workbench publish); the Review screen's re-run model is a `<select>` of the offered models (`Step default` sends none).
- **LLM layer** (`worker/src/ingest_worker/llm/`): providers implement the `LLMProvider`
  protocol (`list_models`, `complete_json`). Kinds: `anthropic`, `openai-chat`,
  `openai-responses`; any OpenAI-compatible local server is an `openai-*` provider with
  `baseUrl`. Model refs are `provider/model-id` or an alias from `config/llm-providers.yaml`
  (`default` → `local/qwen3.8-27b-mtp` on the LM Studio endpoint, `fast` →
  `anthropic/claude-haiku-5-5`). Unresolvable refs raise `ModelResolutionError` and are resolved
  for every extraction *before* any LLM call (config error → `needs_review`, never retried).
- **OCR** (`worker/src/ingest_worker/ocr.py`): `ocr:` in `config/llm-providers.yaml` names a
  vision model (default `local/olmocr-2-7b-1025`), optionally on its own endpoint/key (`OCR_BASE_URL`,
  `OCR_API_KEY` → `ocr.baseUrl`/`apiKeyEnv`, resolved via `ModelRegistry.resolve_ocr`); spec `document.ocr` is `auto|always|never`.
  Providers implement `complete_vision`; tests use `PipelineDeps.render_page` fakes, and only
  `test_render_page_png_scales_longest_side` renders a real PDF (pypdfium2, in-memory).
  OCR output is cached per PDF sha256 + OCR settings (`runs/ocr-cache/`), so re-runs and
  regressions see identical page text.
  Job-level model override beats the spec's model. Discovered models land in `llm_models`
  and populate the UI picker.
- **Data policy:** providers declare `location: local | external` (undeclared = external). Every
  project job carries `params.dataPolicy` (missing = local); the worker refuses an external provider
  for a local-only project before any call, in extraction, OCR (after `resolve_ocr`; the OCR clone
  inherits its named provider's `location`, so an `OCR_BASE_URL` pointing a local-marked provider at a
  remote host is the operator's responsibility), template step re-runs and drafting. Switching a
  project to `local` (`setDataPolicy`) also sets `params.dataPolicy = 'local'` on every existing job
  of the project except segment previews (no model call; strict params), so queued jobs, Retry and
  step re-runs (which reuse the row) cannot go external after a revocation; switching to `external`
  never upgrades old jobs. The `draft` alias (`DRAFT_MODEL`, default the local model) is the
  Workbench drafting model; a drafting call's output budget is `drafting.DRAFT_MAX_TOKENS`.
- Anthropic calls use structured outputs (`output_config.format` json_schema) plus
  `output_config.effort`; refusals (`stop_reason == "refusal"`) raise `RefusalError` → job goes to
  `needs_review`. Don't send `temperature`/`top_p`/`budget_tokens` or assistant prefill — current
  Claude models reject them. OpenAI-compatible providers take an optional `temperature` option;
  the local provider and OCR run at 0 so regression scores measure the template, not sampling noise.
- **Review:** template jobs needing review stop in `awaiting_review` (drafts in the outputs bucket); approve → publish task applies `review_edits` (`worker/src/ingest_worker/review.py`) and writes to the final target (`Target`, `TARGET_S3_*`); approving a test run (`jobs.test`) writes `{job}/reviewed-document.json` to the runs bucket and succeeds without delivering anything (`publish_template_job(deliver=False)`); reject is final. `needs_review` is different: a processing problem for an operator.
- **Results:** `apps/web/src/results/` + `apps/api/src/routes/results.ts` read published outputs from the target store (`AppDeps.targetStore`, `storeFor(stage)`); the API reads `TARGET_S3_*` via `targetConfig` (same fallback as the worker).
- **Workbench ([ADR 0007](docs/adr/0007-workbench.md), [design](docs/design/workbench.md)):** one project per document type (`workbench_projects.id` = template id; `apps/api/src/workbench/`, `apps/api/src/routes/workbench.ts`, `apps/web/src/workbench/`). The Workbench page is the paged project list: it asks `listProjectPage` (`GET /api/workbench/projects`) for one page, counts the filter chips from the server's `facets`, debounces the search by 250 ms (a sequence number drops stale responses), shows up to 3 pinned (`/api/workbench/pins`) and recent (`ih.wbRecent` in `localStorage`, written by `ProjectPage`) projects as cards, and keeps the rows per page in `ih.wbPageSize`. Samples are ordinary documents; uploading one queues a `prepare` job (text + OCR only, `worker/src/ingest_worker/workbench.py`) writing `prepared/{sha256}/text.json|triage.json` to the runs bucket. Sample state comes from that job. Workbench jobs (prepare and test runs) have `priority = -10` (production 0). Prepare jobs never appear on the Jobs page and are never bulk-deleted; while a sample prepares, the worker writes `prepare progress` job events (text layer read, then each OCR page) and, on a `DocumentError`, a `prepare failed` event whose `message` is the review reason; `SampleView.prepare` shows the current attempt's progress only (event at or after the job's `updatedAt`), and `prepareError` trusts a code only while its message equals the job's error (else `other`); pypdf password/read errors in `prepare` go to review instead of being retried; brief history: `GET /api/workbench/projects/:id/briefs` (`briefVersions` in `packages/shared/src/brief.ts`: `changedSections` = `briefDiff` against the previous version, `usedBy` = stages whose newest accepted or partially accepted proposal used that version) and `GET …/briefs/:version`, the Brief tab comparing versions client-side with `briefDiff`; dev test runs are ordinary test jobs. A sample's document is never deleted with a job. Anchor previews are `segment` jobs: project-scoped with no document (`document_id IS NULL`, excluded from every `JobSummary` query by the inner join), `priority = -5`, one per project (a new preview deletes the old; previews for one project serialize via `pg_advisory_xact_lock`). They run `segment.section_spans`, the same code production segmentation uses, in a child process capped at 10 s (`SEGMENT_TIMEOUT_S`); on overrun the child is killed and the job goes to `needs_review` ("…may backtrack catastrophically"), so a runaway anchor regex cannot stall previews or other jobs on the same worker (previews are capped; production segmentation is not, so the Sections tab refuses to save an anchor whose preview timed out). Every grid carries `suggestions` for required sections that miss a segmented sample: `anchor_hints` suggests only for readable anchors (`^Label`, `^(A|B)\b`, optional `(?i)`, leading `\s*`; anything else gets none), tries the anchor's own labels in another case or indented, then `LABEL_VARIANTS` synonyms longest first (never `from`, `bill`, `po`, `terms`, `item`), accepts a synonym only if it looks like a label (colon, end of line or 2+ spaces after, word ends), verifies the rewrite matches the missing sample (`segment_samples` also drops it if it breaks a sample where the section was found), gives one accurate reason per cause (synonym, case, indent), and runs inside the capped child; the Sections tab applies one with a click (unsaved, previewed live). Segment jobs are never retryable or cancellable through the jobs routes: `PgRepo` guards are `document_id IS NOT NULL`, and any query on `jobs` that bypasses `JOB_SELECT` must exclude document-less rows. Idle workers wake on `NOTIFY ih_jobs` (trigger from migration 0009); the poll interval is the fallback (and drives retry backoff). The UI polls a preview every 300 ms with a 30 s deadline. Drafting ([ADR 0007](docs/adr/0007-workbench.md), phase 3a): jobs are document-less `draft` jobs (`priority = -10`, migration 0011). The API sends only ready **dev** samples and `drafting.build_context` refuses anything else; the worker's example template comes from `WORKBENCH_EXAMPLE_TEMPLATE`. Proposals live in `workbench_proposals`, with status derived from the job and the body in `drafting/{project}/{job}.json` (`storage.drafting_key`). Only the admin token can allow external models for a project. External drafting calls are logged as `external model call` job events listing the samples whose text was sent (`samples`, max 8, `MAX_CONTEXT_SAMPLES`) and, in `referencedSamples`, every sample name the sent failures and feedback mention. Drafting stages (phase 3b): stages run in order (`STAGE_ORDER`: survey, outputs, sections, steps); a stage counts as complete once it is accepted or skipped, and stale is derived, never stored. A stale outputs, sections or steps stage can be kept without a proposal (migration 0026 `workbench_stage_confirms`): `POST /api/workbench/projects/:id/stages/:stage/confirm` is 201, 400 `stage X cannot be kept` (survey, references and the rest), 404 unknown project, 409 `stage X is not stale`; the row's `up_to` is the newest earlier completion as read for the check, so a later completion makes the stage stale again (`stageStates` is stale only when an earlier stage completed after `max(completedAt, upTo)`). A kept stage keeps its kind and `completedAt` (a kept skip stays skipped; later stages are unaffected), no proposal is created and the draft is untouched; `StaleBanner` `keepLabel` reads Keep these outputs / anchors / steps. `StageView.skippedAt` is the newest skip, kept after a later run (the Survey "You skipped this stage" banner, `skip` tone). Survey "In brief" is `candidateInBrief`, computed client-side and never stored. The confirmations join `projectFingerprints`, and `deleteProject`'s children include stage confirmations. Change proposals carry `baseVersion` and `baseDefinition`; accepting applies the chosen changes to the open draft, and a change whose target was edited since the proposal is refused (409). The sections stage checks anchors on every dev sample, gives one feedback round, and stores the grid as `anchorCheck`; a segmentation timeout on the final anchor round sends the job to `needs_review`. `run_extraction(check=...)` feeds rules beyond JSON Schema back to the model. The worker drops empty strings/lists from drafted changes before validation, and removes are checked against the draft after earlier changes in the same body. `applyChanges` and `draft_changes.apply_changes` are held in step by the shared fixture, run in TS with `toStrictEqual` (a TS test also parses worker-shaped dumps). References and evaluation (phase 4a): samples are linked to references by PDF sha256. Reference runs are dev test runs with `modelOverride: 'draft'` and `params.forceReview`, so the worker always stops them in `awaiting_review`; the user corrects the values, approves (review finishes, nothing is delivered) and then uses "Save as reference" on the succeeded job. `start('references')` skips samples whose reference run is still queued or running; the references stage is accepted once every ready dev sample is verified, and `start('references')` before the earlier stages are complete is a 409. Evaluate creates project jobs carrying `referenceId`, `modelOverride` and `params.dataPolicy`, and records a `workbench_iterations` row (migration 0013) with a definition snapshot. The scorecard is computed from the jobs, and the summary is cached in `scores` once every job has finished; the evaluation routes rethrow store outages instead of caching a score, and a corrupt or missing document gives a null comparison. Restore writes the snapshot into the open draft. `MemoryRepo` owns the monotonic clock shared by the workbench fake. Feedback and revise (phase 4c): feedback lives in `workbench_feedback` (migration 0015) and can only name dev samples; a feedback `sampleId` must be a READY dev sample and an `iterationId` a dev iteration. `revise` is a change stage outside `STAGE_ORDER`, run as a `draft` job started by `POST /projects/:id/stages/revise`, that cannot be skipped (`StagePanel` `canSkip=false` in the Revise tab), and it may run with no prepared dev samples (feedback alone). Its job params add the open `feedback`, dev-only `failures` from the latest complete dev iteration (the template's own runs first; a model-comparison member only when none is complete), `failuresFrom` (that iteration's `templateVersion` and `model`, shown in the `<evaluation_failures>` header), and `feedbackIds` (only the items actually sent). The worker drops feedback/failures whose sample is not a dev sample filename in params and sends the lowest-scoring failures, capped at `MAX_CONTEXT_SAMPLES`. Accepting a revise proposal, fully or partly, resolves its feedback. Revise skips the anchor round, but a proposal with `putSection`/`setCopies` changes gets one `segment_with_timeout` pass over the dev samples; a timeout sends the job to `needs_review` (no `anchorCheck` is stored). The revise model schema has no union (nullable) types: payload objects are always present with empty sentinels (`""`, `[]`, `0`) that are mapped back to absent, to stay within Anthropic's structured-output limit of 16 union-typed parameters; a test over every stage schema guards this. Holdout and publish (phase 5a, migrations 0016 and 0017): holdout reference runs use the template's own models (`modelOverride: null`, no draft model, since drafting never sees holdout) with `params.forceReview`, started by `POST /api/workbench/projects/:id/holdout/reference-runs` (not a stage); they skip samples that already have a reference or an active run, and refuse with 409 `reference runs are already running` when every unverified holdout sample has an active run. `GET /references?set=dev|holdout` lists either set. Evaluate takes `{ set }` (default `dev`); holdout iterations are visible to the user but ignored by revise (its failures are dev-only), and model comparison stays dev-only. `SampleView.holdoutRuns` is the number of holdout iterations that evaluated the sample, read from `workbench_iterations.sample_shas` (migration 0017, the evaluated samples' sha256 recorded at creation, so the count survives deleted jobs; null rows fall back to the jobs' documents). The publish gate is `publishGate` in `packages/shared/src/evaluation.ts`: the newest complete holdout iteration whose version and definition snapshot equal the open draft and that ran the template's own models (`model === null`; override iterations are allowed for exploration but never count) decides. It passes only when it covered every currently ready holdout sample, compared every sample it evaluated (a job that failed, needs review, was cancelled or deleted fails the gate), and its score is at or above `workbench_projects.publish_threshold` (default 0.9, set with `PATCH /api/workbench/projects/:id`, which records who set it and when: `threshold_set_by` from the token label, `threshold_set_at`, migration 0020, shown under the threshold on the Publish tab). `gateFor` computes those scores from the jobs and caches them per iteration in `workbench_iterations.gate_cache` (migration 0020) under a fingerprint of its jobs (sha256 of each job's `[id, status, updatedAt, referenceId]` in `jobIds` order, a deleted job as `[id, null, null, null]`): a matching fingerprint reuses the cached score, anything else recomputes, and the cache is stored only once no job is queued, running or awaiting review (coverage is always live). Scores compare the raw draft output (never `reviewed-document.json`, so review edits cannot raise a holdout score; dev iterations still use the reviewed document); `GET /api/workbench/projects/:id/publish-gate` shows it. The gate is informational: References and Evaluate are optional stages (`OPTIONAL_STAGES` in `overview.ts`, with Revise; never the next to-do), Publish is `ready` whenever a draft is open, and `POST /api/workbench/projects/:id/publish` publishes any valid draft, recording the gate's iteration and score (null without a holdout run) and never an override (`overrideReason` is still accepted, then ignored; under 10 characters is still a 400). The Template tab's Publish (embedded `TemplateEditor`) calls this route, not the Templates one. The re-check of the draft, the template publish and the publication record happen in one transaction (`WorkbenchRepo.publishDraft`: the template row is locked `FOR UPDATE` and compared with `stableJson`): if the draft changed after the gate was decided, publish is a 409 `the draft changed while publishing; check the gate again`, and if it is no longer an open draft a 409 `no open draft to publish`; either way nothing is written, and a failed publication insert leaves the draft open. Publications are logged in `workbench_publications` (`GET /api/workbench/projects/:id/publications`), and publications from before the gate became informational keep their override reason. A Workbench document type cannot be published from the Templates route (409), and `POST /api/templates/import` with `publish: true` is refused the same way (importing as a draft is allowed). Bundle (phase 6, migration 0019): `export` jobs are document-less, `priority = -10`, one per project (a new export deletes the old export job and its zip, serialized by `pg_advisory_xact_lock(hashtext('export:' || id))`). `bundle.run_export` checks `ExportParams` (`DraftParams` plus `projectName`), refuses holdout samples, verifies each PDF's sha256, builds `context.md` with `drafting.build_context` (the same inputs as the drafting stages: brief, draft, accepted survey, at most `MAX_CONTEXT_SAMPLES` dev samples' text) and writes a deterministic zip to the runs bucket at `exports/{project}/{job}.zip` (`exportKey`/`storage.export_key`); a cancel or delete during the write removes the zip. ## Definition of done

`npm run check` green · new behaviour covered by tests written first · new routes documented · contracts updated on both
sides · docs/ADR updated if architecture changed · no secrets committed.
