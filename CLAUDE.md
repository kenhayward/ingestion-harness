# CLAUDE.md

Content Transformation Studio (CT Studio; repo and code name `ingestion-harness`): ingests PDFs whose structure is known in advance, extracts their contents
through an LLM prompt harness, and writes validated CSV/JSON to S3 (SeaweedFS).

## Architecture in one paragraph

`app` (React, served by nginx) → `api` (Fastify, Node 24/TypeScript) stores the uploaded PDF in
the SeaweedFS **inbox** bucket and inserts a `documents` row + `jobs` row in Postgres. The
`worker` (Python 3.14) claims jobs with `SELECT … FOR UPDATE SKIP LOCKED`, extracts page text
(OCR'ing image-only pages with a vision model, default olmOCR 2), segments it into sections using the document **spec**, runs one LLM call per spec extraction
(JSON Schema-constrained, validated, retried with errors fed back), and writes CSV/JSON to the
**outputs** bucket plus a prompt/response audit trail to the **runs** bucket. Full detail:
[docs/architecture.md](docs/architecture.md). Decisions: [docs/adr/](docs/adr/).

```

```

## Test-driven development — how we work here

1. **Red first.** For every behaviour change, write or extend a failing test, run it, and see
   it fail for the expected reason before touching implementation. Bug fixes start with a test
   that reproduces the bug.
2. **Green minimally**, then refactor with the suite green. Run the narrowest test command while
   iterating, and `npm run check` before declaring work done.
3. **Never weaken a test to make it pass** (deleting assertions, loosening matchers, adding
   skips). If a test is wrong, say why and fix it deliberately.
4. **Ports and adapters keep tests fast and offline.** Unit tests never touch the network,
   Postgres, SeaweedFS, or a real LLM:
   - API: `buildApp({ repo, store, specs, … })` with `MemoryRepo` + `MemoryObjectStore`;
     exercise routes with `app.inject()` (see `apps/api/test/helpers.ts`).
   - Web: components receive an `Api` prop; tests use `fakeApi()` from `apps/web/test/fake-api.ts`
     and Testing Library queries by role/label (not class names).
   - Worker: `PipelineDeps` takes `MemoryObjectStore`, a `TextExtractor` lambda (no real PDFs
     needed), and a `ModelRegistry` of `FakeProvider`s; queue behaviour via `FakeQueue`
     (`worker/tests/fakes.py`). Provider adapters are tested against stub SDK clients
     (`tests/test_providers.py`) that assert the exact request shape.
   - Code needing real infra (PgRepo, PgJobQueue, S3 stores) gets integration tests marked
     `@pytest.mark.integration` (excluded by default) or under `apps/api/test/integration/`.
     `npm run test:integration` runs the API ones (own config). The workbench Pg test skips unless `IH_TEST_DATABASE_URL` is set; point it at a throwaway Postgres
     (they apply `db/migrations` and write rows), e.g. `docker build -f deploy/docker/postgres.Dockerfile -t ih-postgres:pgvector deploy/docker`
     once (Postgres 17 with pgvector, needed from migration 0035), then `docker run --rm -d --name ih-test-pg -e
     POSTGRES_PASSWORD=test -p 55433:5432 ih-postgres:pgvector`, then
     `IH_TEST_DATABASE_URL=postgres://postgres:test@localhost:55433/postgres npx vitest run --config apps/api/vitest.integration.config.ts workbench-pg`.
     External S3 targets are reached by the delivery bridge's `s3` sink (ADR 0017): its probe checks an external target's bucket (HEAD, 404 = `no such bucket`) before writing, since SeaweedFS creates a missing bucket on the first put where AWS answers `NoSuchBucket` (internal targets' buckets are created on save). `deploy/scripts/external-s3.ps1 up` (or `.sh`) still starts a throwaway SeaweedFS outside the stack for trying an external target by hand.
5. **Contract tests stay green**: both `apps/api/test/spec-registry.test.ts` and
   `worker/tests/test_specs.py` load every spec in `specs/`. A new spec is not done until both pass.
6. New pure logic (segmentation, CSV flattening, retry policy, alias resolution) should be
   table-driven/parametrised tests — cheap to extend when a new document quirk turns up.

## Rules of the road

- **Templates live in the database** (`templates` table, migration 0003; `apps/api/src/templates/`, `apps/web/src/templates/`): drafts editable, published immutable (DB triggers too), YAML import/export, `specs/*/template.yaml` seeded on API start. The worker loads a job's template from the DB first (`pipeline.load_definition`), files second. Draft test runs set `jobs.test` and are never delivered to the target (approving one only finishes review). Every write to a draft records a `template_changes` row for every document type, not only Workbench ones (migration 0029, append-only, `ON DELETE CASCADE` from its version, so `deleteDraft` takes the log; published rows are never written and the 0003 triggers are untouched) in the same statement (a data-modifying CTE in `PgTemplateRepo`): `hand` saves (`PUT …/versions/:version`, also the Sections tab's anchor saves), applied `proposal`s (with `stage`, `proposal_id`; ` (n of m proposed changes)` when partly accepted), `restore`d iterations, the draft's `started` entry (new type v1, next draft "from published vN", Workbench project creation) and `import`s (YAML as a draft, bundles); summaries and diff chips come from `describeDefinitionChange`, and a write that changes nothing (`count` 0, an absent list = `[]`) logs nothing, nor do published creates (seed, published import). A save may carry `baseUpdatedAt` (both editors send it): when the draft was written since, nothing is saved or logged and the answer is a 409 `the draft changed since you opened it; reload it to see the changes` (Pg compares `updated_at` truncated to the millisecond, since it keeps microseconds and the API's ISO strings milliseconds); the editors disable Save while a save is in flight (a double click would otherwise 409 against its own first save) and offer *Reload the draft*. Accepting a proposal and restoring an iteration pass the `updatedAt` of the draft they read as `expectedUpdatedAt`: a write in between (a hand save) is a 409 `the draft changed while applying; try again` with nothing written or logged (a draft that was published meanwhile keeps the `…no longer open` wording). Renaming a document type (`PUT /api/templates/:id/name`, `renameTemplate`; the Document types card's *Rename…*, `RenameDialog`; refused for a retired type) writes the trimmed name (1-200 characters) into the open draft as a `hand` change `Renamed “old” to “new”` (under `expectedUpdatedAt`: a write in between is a 409 `the draft changed while renaming; try again`), starting the next draft from the latest version first when none is open (published versions keep their name), and renames the Workbench project at once (`WorkbenchRepo.renameProject`); the same name changes nothing and starts no draft.
- **Version labels (issue #144, migration 0045):** every recipe version may carry a `label` (1-80 chars) and a `note` (1-2,000) with `label_set_by`/`label_set_at` (`VersionLabelBodySchema`, `PublishLabelSchema`, `VersionLabelSchema`, `versionName` in `packages/shared/src/version-labels.ts`; `TemplateRecord` carries them, `TemplateRepo.setLabel`). Metadata only, never part of the definition: the 0003 trigger guards `definition`/`status` alone, so published versions take labels; setting one leaves `updated_at` alone (the editors' `baseUpdatedAt` still matches) and logs nothing in `template_changes`; the worker never reads it. Routes (`routes/templates.ts`): `PATCH /api/templates/:id/versions/:version` (a field left out is kept, `null` clears; retired types too), `GET /api/templates/:id/versions` (newest first, no definition; `GET /api/templates` `versions[]` carry `label`), `POST /api/templates/:id/versions/:version/restore` `{ from, baseUpdatedAt? }` (writes version `from` into the open draft as a `restore` change ` (from vN · label)`; nothing written when equal; 409 `{id} v{n} is not an open draft` or the stale-draft message). Both publish routes take optional `label`/`note`, set on the draft first. A new draft's `started` entry names its source's label. Web: the recipe editor's *Versions* sub-tab (`VersionsPanel`, both editors; outside the read-only fieldset): label and note per version, *Replace draft vN with vM* (confirm `Dialog`, disabled while edits are unsaved) or *Start vN from vM* when no draft is open; publish keeps the draft's label (no publish dialog).
- **Retired document types (migration 0030):** an admin retires or unretires a type (every version, recipe or legacy spec) with `PUT|DELETE /api/specs/:id/retirement` (admin-only, logged `document type retired`/`unretired`; retiring again keeps the first retirement; unretiring a type that is not retired is a 204; unknown is a 404). The row (`document_type_retirements`: `type_id`, `retired_at`, `retired_by` = the user's name) lives with the type, not a version, so seeding a missing `specs/*/template.yaml` version keeps the type retired, and deleting a never-published Workbench project removes it. Nothing is deleted and everything stays readable, except what the type delivered: retiring withdraws it (ADR 0011 step 7: `IngestionRepo.withdrawType` marks its jobs' published outputs `job_outputs.withdrawn_at` (migration 0037), forgets its current graphs and queues one `withdraw` job, on every PUT, idempotent (it never repeats a failed withdrawal: `withdrawalStatus.failed` counts failed and needs-review ones for the Linked data panel); readers skip withdrawn outputs; the worker's withdrawal spares what was delivered again since, checked under each graph's lock (`GraphRegistry.locked`, `RebuildSource.object_live`)), and unretiring queues a `republish` (`republishType`) that re-delivers them from each job's reviewed document, else its draft, with its own recipe version (nothing if the type was retired again; graph before the record; legacy spec outputs are skipped and stay withdrawn). Hidden: `GET /api/specs` by default (`?retired=include` lists them with `retired`; every row carries `kind`; Jobs, Home and Results ask for them so old jobs keep their names; the upload strip never offers one), the Document types page always (no toggle), the Workbench list by default (`retired=include` for API callers, no toggle in the web; `ids=` still returns them, so pinned and recent cards show them with a *Retired* tag and the project URL opens). `GET /api/templates` and every `ProjectView` carry `retired`; the Workbench list overlays it live (never cached; `LIST_CACHE_VERSION` 4). New work is a 409 `<name> is retired: unretire it to use it again` (`retiredProblem`, the `refuseRetired` preHandler): uploads and Templates test runs, retry/re-process of any of its jobs, regression runs, a new type under a retired legacy id, new drafts, publishing (both routes), YAML import, Workbench project creation, bundle import under that id, sample uploads, dev test runs, every drafting stage, holdout reference runs, re-verify, evaluate and compare. Allowed: reading, edits that queue no job (draft, brief, feedback, proposals, skip/keep, restore, policy, threshold, sample role), deletes, cancel, review of jobs already awaiting review (approve, reject, step re-run), saving a reference, anchor previews and bundle export. Jobs already queued or running finish (the worker is unchanged). Web: admins retire any type, recipe or legacy, from the Document types page (*Retire…* and a confirm `Dialog`, `RetireDialog`); the page lists file-only legacy `spec.yaml` types as read-only cards (`legacyTypes` in `apps/web/src/templates/legacy.ts`: `kind: 'spec'` rows of `GET /api/specs` with no database recipe; tag *Legacy spec (file)*). **Unretiring is API-only**: there is no Unretire button anywhere and no `unretireType` in the client; `RetiredBanner` (project page, standalone recipe editor) and the *Retired* tags say who retired the type, when, and name `DELETE /api/specs/{id}/retirement` (`unretireHint`). A retired type's recipe editor is read-only (like a published version). The web disables each job-creating button with `RETIRED_REASON` (`apps/web/src/ui/retired.ts`); the Jobs page and Runs tab Retry buttons are not pre-disabled (the dialog shows the 409).

  edit an applied one). `migrationNameProblems` (`apps/api/src/db/migration-names.ts`, its test reads
  `db/migrations`) refuses a new numbered file, a malformed or unreal timestamp and a shared one. A

  `ingest-worker <version>` at start. No GitHub Releases yet.

reference and evaluation runs and runs from before batches have `batchId: null`. `GET /api/queue/summary` (any signed-in user, counts only) gives `ahead` (queued jobs with a document: production, prepare, publish, rerun and earlier Workbench runs; document-less drafting, segment and export jobs are not counted), `running` and a rough `etaSeconds = ceil(ahead × median / max(1, running))` (`queueSummary`, `IngestionRepo.queueStats`; the median is over the 50 newest succeeded or awaiting-review runs that finished in the last 24 h; null without history, 0 for an empty queue). A sample's document is never deleted with a job. Anchor previews are `segment` jobs: project-scoped with no document (`document_id IS NULL`, excluded from every `JobSummary` query by the inner join), `priority = -5`, one per project (a new preview deletes the old; previews for one project serialize via `pg_advisory_xact_lock`). They run `segment.section_spans`, the same code production segmentation uses, in a child process capped at 10 s (`SEGMENT_TIMEOUT_S`); on overrun the child is killed and the job goes to `needs_review` ("…may backtrack catastrophically"), so a runaway anchor regex cannot stall previews or other jobs on the same worker (previews are capped; production segmentation is not, so the Sections tab refuses to save an anchor whose preview timed out). Every grid carries `suggestions` for required sections that miss a segmented sample: `anchor_hints` first tries any anchor, readable or not, that misses only because the sample has a no-break or other Unicode space where the anchor has a plain one (`_space_fix`: literal spaces outside a class become `\s`, U+00A0 is added after a space inside one, verbose patterns are skipped; the reason names the character and quotes the line); otherwise it suggests only for readable anchors (`^Label`, `^(A|B)\b`, optional `(?i)`, leading `\s*`; anything else gets none), tries the anchor's own labels in another case or indented, then `LABEL_VARIANTS` synonyms longest first (never `from`, `bill`, `po`, `terms`, `item`), accepts a synonym only if it looks like a label (colon, end of line or 2+ spaces after, word ends), verifies the rewrite matches the missing sample (`segment_samples` also drops it if it breaks a sample where the section was found), gives one accurate reason per cause (synonym, case, indent), and runs inside the capped child; the Sections tab applies one with a click (unsaved, previewed live). Segment jobs are never retryable or cancellable through the jobs routes: `PgRepo` guards are `document_id IS NOT NULL`, and any query on `jobs` that bypasses `JOB_SELECT` must exclude document-less rows. Idle workers wake on `NOTIFY ih_jobs` (trigger from migration 0009); the poll interval is the fallback (and drives retry backoff). The UI polls a preview every 300 ms with a 30 s deadline. Holdout and publish (phase 5a, migrations 0016 and 0017): holdout reference runs use the template's own models (`modelOverride: null`, no draft model, since drafting never sees holdout) with `params.forceReview`, started by `POST /api/workbench/projects/:id/holdout/reference-runs` (not a stage); they skip samples that already have a reference or an active run, and refuse with 409 `reference runs are already running` when every unverified holdout sample has an active run. `GET /references?set=dev|holdout` lists either set. The publish gate is `publishGate` in `packages/shared/src/evaluation.ts`: the newest complete holdout iteration whose version and definition snapshot equal the open draft and that ran the template's own models (`model === null`; override iterations are allowed for exploration but never count) decides. It passes only when it covered every currently ready holdout sample, compared every sample it evaluated (a job that failed, needs review, was cancelled or deleted fails the gate), and its score is at or above `workbench_projects.publish_threshold` (default 0.9, set with `PATCH /api/workbench/projects/:id`, which records who set it and when: `threshold_set_by` from the user's name, `threshold_set_at`, migration 0020, shown under the threshold on the Publish tab). `gateFor` computes those scores from the jobs and caches them per iteration in `workbench_iterations.gate_cache` (migration 0020) under a fingerprint of its jobs (sha256 of each job's `[id, status, updatedAt, referenceId]` in `jobIds` order, a deleted job as `[id, null, null, null]`): a matching fingerprint reuses the cached score, anything else recomputes, and the cache is stored only once no job is queued, running or awaiting review (coverage is always live). Each due watch's cycle runs between jobs under a session advisory lock (one poller across workers), and every bridge call acts as the watch's run-as user. Rulings: create lists the root as the signed-in admin (422 `source_test_failed`) and the watch runs as them; a change of folder or target (stopped only, 409 `stop the watch first`) runs the watch as the editing admin, after listing the new root as them; **stop now** cancels the jobs of documents not yet at the bridge and counts them as failed (`WATCH_CANCELLED_DETAIL`; a running job's item is failed by the worker, so a delivery the bridge accepted is never recorded as cancelled), files stay where they are; **drain** takes nothing new, a draining watch still admits files it took before the drain, and stops itself once nothing is unfinished; **start** clears the problem and retries the stuck moves (pickups refused `MAX_MOVE_TRIES` 5 times, which show as the watch's problem); remove only while stopped (the batch stays as history). A watch's batch is never re-run in place (409 `watched`, `WATCHED_REFUSAL`: upload the file again); a target a watch names is in use (`TargetUsage.watches`). The worker reads `APP_PUBLIC_URL` (optional, the reason file's batch link) and `MAX_UPLOAD_MB`. Revise (`ReviseTab`, `ReviseFeedback`, helpers in `workbench/revise.ts`) follows handoff §9 and no longer uses `StagePanel`: a warn banner when another drafting stage has a proposal waiting, the *What the model will see* card from the RV1 preview (your numbered feedback, only what the preview sends, the rest listed as not sent, with the add form's ids filled from the draft and never a sample or run; the latest dev run's failures worst first with diff chips; the violet *Not sent* note), the running strip, the proposal card with *Answers* badges (`ProposalCard` `badge`/`footerNote`), ANSWERED feedback and *Evaluate vN on dev…* after Apply (a button, not a link: the re-process dialog starts `startEvaluation(…, { set: 'dev' })` from the tab, shown in the "no complete dev run" note instead when no applied card offers it; a running dev evaluation of the draft shows as a status strip with progress and the tab polls until it completes, so the failures sent refresh; changes that would add, remove or reshape outputs say so in the footer before Apply, `outputChanges` over `applyChanges`), and Earlier revisions (no version: `ProposalView` has none); Ask is disabled without a draft, feedback or drafting model, and the tab tells the page (`onChanged` → overview reload) after feedback, Ask, Reject and a finished revision.
- **Error routing in the worker:** `DocumentError` (missing sections, page count, schema never
  satisfied, refusal, `PrepareFailed` in prepare only, a model the server does not have: `llm.base.ModelUnavailableError`,
  raised by the adapters from `is_model_unavailable` (LM Studio "Invalid model identifier", OpenAI/vLLM "does not exist",
  Ollama/llama.cpp "not found", Anthropic 404; never retried whole when streamed), routed by `ocr_pages` and
  `run_step_extraction` with `model_unavailable_reason` and by drafting and mapping with `drafting.unavailable_reason`;
  a request too long for the model's loaded context window:
  `llm.base.ContextExceededError`, raised by the adapters from `is_context_exceeded` (LM Studio, OpenAI, vLLM,
  llama.cpp, Ollama, Anthropic wordings; a streamed one is not retried whole), routed by `ocr_pages` and
  `run_step_extraction` with `context_exceeded_reason` (stage, model ref, what to lower) and by drafting and
  mapping with `drafting.context_reason`) → `needs_review`, not retried. Anything else → `fail()` → re-queued with
  backoff until `max_attempts`, then `failed`.
  `JobCancelled` (operator cancel, ADR 0005) → no status write; worker status writes are guarded
  `AND status='running'` so a cancel always wins. **One job, one worker:** a claim takes a queued
  job with `FOR UPDATE SKIP LOCKED`, and while it runs a thread beats `jobs.heartbeat_at` every
  `HEARTBEAT_S` (60) on its own connection, guarded like a status write (`heartbeat.py`,
  `PgJobHeartbeat`, `beating`; migration 0042, which also makes `jobs_notify_changed` ignore a
  beat). The reaper re-queues a running job only when its heartbeat (else its claim time) is older
  than `STALE_LOCK_S` (900): its worker stopped (a redeploy), whatever its attempts (`run_once`
  warns past the limit), so `WORKER_REPLICAS` > 1 never runs a long job twice. A run whose job was
  taken anyway stops at its next `check_cancelled`, and embedding checks between batches
  (`embed_version(stop=)`); a retried ontology import whose version is already `ready` only
  finishes its embedding (`OntologyStore.ready`), since saving its terms again would cascade-delete
  the embeddings.
- **Word documents ([ADR 0009](docs/adr/0009-word-documents.md), [design](docs/design/word-documents.md)):** a `.docx` source is converted to PDF by the `converter` service (Gotenberg `8.38.1-libreoffice`, compose network `converter` with `internal: true`, only the worker joins it, `CONVERTER_URL`) before the pipeline, which then runs unchanged. `pipeline.load_source` reads the inbox object, judges `.docx` by its content types (`convert.is_docx`; never a file name: LibreOffice turns any bytes into a text PDF; anything else is read as a PDF as before), and caches the PDF at `converted/{sha256}/{fingerprint}.pdf` in the runs bucket (`storage.converted_key`; fingerprint `gotenberg-{version}-c{CONVERT_VERSION}`; an invalid entry is re-converted). A document's identity is the uploaded file: `Source.sha256` (the `.docx`'s hash, = `documents.sha256`) keys prepared text and the OCR cache, never the PDF's hash (LibreOffice embeds a creation date). Word's Symbol and Wingdings characters (`<w:sym w:font="Symbol" w:char="F0B0"/>`, a degree sign) reach the PDF's text as private-use code points U+F000-U+F0FF; `pdf.extract_pages` translates them per page with `symbol_fonts` (`SYMBOL`, `WINGDINGS`; `font_family` of each font's `/BaseFont`, `private_use_codes` of its ToUnicode map, `translation`: a code only one family's fonts produce, else left as is), for every PDF, not only converted ones; prepared text written before stays as it was until the sample is prepared again. `ConversionRejected` (a 4xx, a 500 `LibreOffice failed to convert…`, a non-PDF 200) → `needs_review`; `ConverterUnavailable` (transport, timeout, other 5xx) is retried; no converter configured → `needs_review`. Tests use `FakeConverter` (`tests/fakes.py`); `tests/test_convert_integration.py` (marked `integration`) needs `CONVERTER_URL` (dev-infra publishes the converter on `localhost:3010`). Uploads (`POST /api/documents`, Workbench samples, bundle import) go through `checkSource` (`apps/api/src/uploads.ts`): a PDF, or a `.docx` (not `.docm`/`.dotx`/other OOXML; 415 `file is not a PDF or Word document (.docx)`) without tracked changes (`<w:ins|del|moveFrom|moveTo` in the body, headers, footers, footnotes or endnotes: 422), inflating only those parts under a 64 MiB cap. The inbox key's extension records the kind (`inboxKey(…, ext)`), and `JobSummary`/`ResultSummary.contentType` derive from it (`sourceContentType`; no column, since document rows copied for test, reference and regression runs share the key); `GET /api/jobs/:id/document` serves a `.docx` as an attachment. Bundles carry samples as uploaded (`samples/<sha256>.docx` for Word), and import checks each like an upload and against its extension. The CI smoke test uploads `deploy/scripts/fixtures/smoke.docx` as a Workbench sample and waits for it to be prepared (2 pages; no model call). The upload strip also takes dropped folders (`readDrop` in `apps/web/src/jobs/folder-drop.ts`: entries taken during the drop event, subfolders walked, only `isSourceFile` files listed in path order, hidden files/folders and `~$` Office lock files left out; a drop without a folder is handled synchronously as before) and shows one line per folder (`folderNote`: `Name: n files to process · k other files left out`). The web's upload inputs take `SOURCE_ACCEPT` and filter with `isSourceFile` (`apps/web/src/documents.ts`; by type or `.pdf`/`.docx` name, since browsers often send no type for `.docx`), and a Word job or result offers "Download original (.docx)" (`isWordDocument(contentType)`) instead of "Open PDF".
- **Capabilities as nodes ([ADR 0018](docs/adr/0018-capabilities-as-nodes.md), [design](docs/design/worker-nodes-refactor.md)):** worker nodes take and return typed values (`read_pages`, `select_pages`, `segment_pages`, `run_step`, `normalise_step`, `finalise`; a recipe's steps pass a frozen `DocState`), each described in `nodes.py` (`NodeSpec`: `effects` pure/cacheable/effectful, `egress` none/model/remote; tests hold `NODES` to the functions); `JobModels` is the only way to a chat, vision or OCR model and checks the data policy (a source test refuses `models.resolve(` outside `llm/`); `run_nodes` gives every node a cancellation safe point; handlers in `main.TASKS` (exactly the tasks `jobs_task_check` allows) return `Complete`/`AwaitReview`/`Deliver` and `apply_outcome` alone writes the status. `tests/test_equivalence.py` pins everything a job does to golden files (`IH_UPDATE_GOLDEN=1` rewrites them, only on purpose).
- **LangGraph trial ([design](docs/design/langgraph-trial.md), [ADR 0018](docs/adr/0018-capabilities-as-nodes.md)), off by default:** `WORKER_STEP_GRAPH=langgraph` runs a recipe's steps as a LangGraph graph (`step_graph.py`) checkpointed in Postgres schema `langgraph` (`postgres_checkpointer`), so a job whose worker stopped resumes at its step; one thread per run of a job (`thread_key`), deleted unless a retry will resume it (`step_thread`), and pruned at worker start and hourly unless its job is queued or running (`ThreadPruner`, `ORPHANS_SQL`, `pg_orphaned_threads`, `prune_threads`; a failed prune is logged, never fatal); LangSmith tracing is always forced off (`tracing_context(enabled=False)`, tested: it would send document text). Unset, the steps run through `run_nodes` as before; `tests/test_equivalence.py` runs every scenario through both. Real-Postgres and killed-worker tests: `tests/test_step_graph_integration.py` (`IH_TEST_DATABASE_URL`).
- **A step's model log:** the Pipeline tab's retry warning (`retryWarning`, `StepFigures` `onShowLog`, both editors) opens `StepAttemptsDialog` (`templates/StepAttemptsDialog.tsx`; with `jobId` instead of `templateId` it shows one job's attempts: the Review page Steps tab's *Model log*): `GET /api/templates/:id/steps/:step/retried-runs` (`RetriedRunsSchema`, the newest `MAX_RETRIED_RUNS` 10 non-cached runs with more than one attempt, one per job, from `repo.metricsData`) on the left, and `GET /api/jobs/:id/steps/:step/attempts` (`StepAttemptsSchema`: the worker's audit files `{job}/{step}[.part]/attempt-{n}.json` in the runs bucket, grouped by call, `step` first, corrupt files left out; 404 `no saved attempts for step {step} of this job`) for the run opened; schemas in `packages/shared/src/step-attempts.ts`, routes `apps/api/src/routes/step-attempts.ts` (designers and admins; operators refused).
- **The step cache is workbench-only:** production, regression and re-run jobs never read or write it (`template_pipeline.workbench_step_cache` returns `None` for them).
- **Never call real LLM APIs from tests or CI.** No API keys in the repo; secrets live in
  `deploy/.env` locally (git-ignored) and `/etc/ingestion-harness/<env>.env` on deploy hosts.
- TypeScript: ESM with `.js` import suffixes, Zod at every boundary (env, request bodies,
  specs), no `any` without a comment. Python: `mypy --strict`, ruff, dataclasses/Pydantic,
  `from __future__ import annotations`.
- Keep `apps/api` free of LLM logic and `worker` free of HTTP-serving logic.

## CI/CD

Public repo (Apache-2.0). **CI runs on GitHub-hosted runners**; only deploys use self-hosted
runners on the deploy hosts. Never target a self-hosted runner from a `pull_request` workflow
(see [docs/runners.md](docs/runners.md)). `main` is protected: PRs only, CI must be green.
`ci.yml`: node + worker jobs, then images build + compose smoke test, all three required checks on PRs; a push to `main` runs only the `tag` job (strict required checks mean the PR already passed them up to date with `main`). `deploy.yml`: main →
staging after green CI (once repo variable `AUTO_DEPLOY_STAGING=true`); manual dispatch for production / rollbacks (`no_build` + older ref).

sides · docs/ADR updated if architecture changed · new help topics listed in the Help panel (`HELP_INDEX`) · today's release note
updated with the change (`docs/release-notes/`) · no secrets committed.
